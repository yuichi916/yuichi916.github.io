# #01 Claude Codeに頼んだのに「思ってたのと違う」をなくす｜作らせる前に決めさせる

Claude Code や Codex、Cowork に頼んだら、ちゃんと完成しているのに、思っていたのと違うものが返ってきた。そんな人に向けて、作らせる前の数分でそれを防ぐ方法を書きます。

---

## 完成しているのに、違う

「いい感じにまとめて」「モダンなデザインで」「使いやすいツールにして」。

そう頼むと、AIエージェントは本当に最後まで作ってくれます。エラーもなく、見た目も整っていて、報告も丁寧です。

でも、開いてみると、違う。

どこが、と聞かれるとうまく言えない。直してもらおうとすると、また別の「違う」が返ってくる。

エンジニア437人に聞いた調査では、AIへの不満の1位が「意図と異なるものが生成される」で、54.9%でした。AIエージェントの失敗1,642件を分類した研究でも、原因の最多は「仕様」の問題で、41.8%です。

いちばん多い「こんなはずでは」は、これです。

---

## 以前の私：「背景が真っ黒」としか言えなかった

3Dの背景を頼んだときのことです。

1枚目が出てきて、私が返した言葉は「背景が真っ黒」でした。2枚目、3枚目と作り直してもらっても、何かが違う。けれど、何が違うのかを言う言葉を持っていませんでした。

同じ場所の背景を、2日半で6回作り直しています。

あとで6枚を並べて測ってみると、1枚目と6枚目の明るさはほとんど同じでした。1枚目が暗かったのは、物が何も置かれていなかったから。6枚目が暗いのは、物で埋まったうえで光を落としていたからです。私の「真っ黒」は、この2つを区別できない言葉でした。

## 今の私：作る前に、AIのほうから聞いてくる

先日、Claude Opus 5.5 の紹介動画をXに出したときは、違いました。

私の最初の指示は、これだけです。

「Opus5.5がリリースされたので、よくなったことを簡潔にまとめてXに投稿したい。紹介ビデオもあるといい」

エージェントは作り始める前に、2つ聞いてきました。どのアカウントに投稿するか。動画をどんな見た目にするか。選択肢つきです。私は選ぶだけでした。

そこから公開まで、約1時間。私がやり直しを頼んだのは、公開後に1行目を書き直させた1回だけです。

違ったのは、AIの賢さではありません。**作る前に、決めるべきことが私の前に並んだかどうか**でした。

---

## なぜ「思ってたのと違う」が起きるのか

人が手で作っていた頃、曖昧な指示はそれほど怖くありませんでした。書き始めれば、手が止まるからです。「ここ、どうするんだっけ」で作業が止まり、そこで考え直す機会が来ました。

**実装が遅いあいだは、その遅さが、考え直すための検問所になっていました。**

AIエージェントは、曖昧な指示の前でも止まりません。決まっていないところを、もっともらしい平均で埋めて、完成まで持っていきます。だから、失敗の形が変わりました。

| | 人が作っていた頃 | エージェントに任せる今 |
|---|---|---|
| 曖昧な指示を受けると | 手が止まる | 止まらない |
| 失敗の形 | 未完成 | 完成しているが違う |
| 気づく時期 | 作業中 | できあがってから |
| 捨てるコスト | 時間 | 時間＋「もったいない」 |

最後の行が厄介です。1時間で完成品が出てくると、方向が違っていても捨てにくい。「直せば使えるかも」と手を入れ続けて、次の回で書く修正地獄に入っていきます。

もう一つ。私が作っているAIエージェントの能力の地図には、「エージェントは実行の途中で、確認の質問ができない」という報告を載せています。任せて走らせているあいだは、最初の誤解がそのまま最後まで伝わる。だから、聞き返しは作る前に済ませておくしかありません。

---

## この回を読むと、できるようになること

- 頼む前の数分で、「何を決めればいいか」を、AIに出させられるようになる
- 決めたことを、AIに間違いなく渡せるようになる
- 頼んでいない機能や変更を、勝手に足させずに済むようになる

そのために、そのまま打てる依頼文5つと、CLAUDE.md にそのまま置ける規約、着手前のチェックリストを渡します。

---

## 今日から使える1文

何かを頼むとき、最初にこれを打ってください。

```
この作業で私が決めないといけないことを、重要な順に5つ挙げて。
それぞれ選択肢と、選択が結果に与える違いも書いて。
```

何を決めるべきかを知らないうちは、良い指示は書けません。だから、質問ごと出させます。

3Dの背景でこれを打つと、「視点の高さ」「霧の量」「光源の色温度」「素材の密度」が並びます。「真っ黒」しか言えなかった頃の私の前に、この4つがあれば、選ぶだけで済んだはずです。

資料でも、ツールでも、文章でも同じように使えます。

## ここから先にあるもの

1. **頼む前の手順を1枚に**。規模の宣言から、着手の許可まで
2. **着手前の3行**（出力・入力・確かめ方）と、資料・ツール・文章それぞれの記入例
3. **そのまま打てる依頼文5つ**。決めさせる／1問ずつ聞かせる／案を比べさせる／壊れ方を先に言わせる／許可するまで作らせない
4. **Claude Code の plan mode の使いどころ**と、Cowork・ChatGPT で同じことをするやり方
5. **頼んでいないことを足させない規約**。CLAUDE.md や AGENTS.md にそのまま置けます
6. **やりがちな失敗6つ**と、着手前のチェックリスト

## 1. 頼む前の手順

| 順 | やること | かかる時間の目安 |
|---|---|---|
| 1 | 規模を宣言させる（調べる／限定／構造） | 数秒 |
| 2 | 着手前の3行を書く（出力・入力・確かめ方） | 1〜3分 |
| 3 | 「決めること5つ」を出させて、1問ずつ答える | 3〜10分 |
| 4 | 案を2〜3個出させて、選ぶ | 数分 |
| 5 | 壊れる場面を3つ言わせる | 1分 |
| 6 | 設計を見て「これでいい」と言うまで、作らせない | 1分 |

小さな依頼なら、2〜6は合わせて2〜3行で終わります。**省くのではなく、短くします。**

公式のおすすめも同じ考え方です。Claude Code の公式ドキュメントは、「調べる → 計画 → 作る」の順に進め、変更を1文で説明できるほど小さな作業なら計画は省いてよい、としています。

「単純だから確認はいらない」と思ったときが、いちばん危ないときです。単純な依頼ほど、前提が確かめられないまま進みます。私の多言語版で全言語が日本語になった事故も、「翻訳が無ければ原文を出す」という、それ自体は正しい仕組みを足したときに起きました。

---

## 2. 規模を宣言させる

すべての依頼に重い手順を課すと、そのうち守らなくなります。だから最初に、この依頼がどの重さかを決めます。

| 区分 | 中身 | 手順 |
|---|---|---|
| 調べる | 「できるか？」を確かめたいだけ | 答えだけもらう。作ったものは捨てる前提 |
| 限定 | 既にあるものへの小さな変更 | 短い設計を口頭で確認してから |
| 構造 | 新しく作る。複数の場所に影響する | 決めること → 案の比較 → 設計 → 計画 |

迷ったら重い方を選びます。途中で複雑さが見つかったら、その場で格上げして宣言し直させます。逆（格下げ）はしません。

```
この依頼の規模を「調べる／限定／構造」のどれかで最初に宣言して。
迷ったら重い方。途中で複雑さが分かったら、格上げして宣言し直して。
```

## 3. 着手前の3行

エージェントに頼む前に、自分でこの3行を書きます。書けない行があれば、そこが最初の仕事です。

```
出力: 何ができあがれば終わりか
入力: 渡せるもの（資料・データ・URL・既存のファイル）
確かめ方: できたものが正しいと、どうやって分かるか
```

**記入例：資料**
```
出力: 部長向けのA4 1枚。結論が最初。来週の会議で「予算を取る／取らない」を決めてもらう
入力: 先月の売上表（sales.xlsx）、競合3社のURL
確かめ方: 数字は sales.xlsx と一致する。結論→理由3つ→数字の順。1枚に収まる
```

**記入例：ツール**
```
出力: 請求書のPDFを読んで、日付・取引先・金額をCSVに書き出すスクリプト
入力: 見本のPDF 5枚（invoices/）
確かめ方: 5枚すべてで、手で書いた正解のCSV（answer.csv）と一致する
```

**記入例：文章**
```
出力: 採用ページの紹介文、400字。読み手は転職を考えている30代のエンジニア
入力: 社員インタビューのメモ（interview.md）
確かめ方: メモにない事実を書いていない。400字±20字。「成長」「挑戦」を使わない
```

3行目がいちばん大事です。「自分が読んで、なんとなく」としか書けないなら、その作業は、AIに任せる範囲を一段狭くします。確かめ方の作り方は、#04で詳しく書きます。

## 4. そのまま打てる依頼文5つ

### 依頼文1：決めさせる

```
[やりたいこと]をしたい。
作り始める前に、私が決めないといけないことを、重要な順に5つ挙げて。
それぞれ選択肢と、選択が結果に与える違いも書いて。
```

### 依頼文2：1問ずつ聞かせる

```
決めることを、1つずつ質問して。私が答えたら次へ進んで。
各質問には選択肢を2〜4個つけて、おすすめがあれば1つだけ理由つきで示して。
```

まとめて5つ聞かれると、人は雑に答えます。1問ずつ答えていくと、自分でも決まっていなかったことに気づきます。**質問の目的は、情報を集めることではなく、あなたに決めさせることです。**

### 依頼文3：案を比べさせる

```
案を3つまで出して。各案に次を書いて。
- 狙い（何を優先したか）
- 捨てたもの
- この案が失敗するとしたら、どんな場面か
どれが良いかの推薦は、最後に1行だけ。
```

1案だけでは、良いのか悪いのか判定できません。2案の差なら判定できます。**差が、そのまま評価の軸になります。**

案は3つまでにします。5つ出させると選べなくなり、「おまかせで」に倒れます。推薦を最後に1行だけにするのは、先に読むと、選ぶ前に引っぱられるからです。

### 依頼文4：壊れ方を先に言わせる

```
この設計が破綻する場面を3つ挙げて。それぞれ、起きたら何が見えるかも書いて。
```

いちばん費用対効果の高い質問です。全言語が日本語になった事故は、この問いを飛ばしたときに起きました。「翻訳ファイルが公開されていなかったら？」と一度でも聞いていれば、答えは返ってきていたはずです。

### 依頼文5：許可するまで作らせない

```
設計を短く見せて。私が「これでいい」と言うまで、作り始めないで。
設計が2文でも、この確認は省かないで。
```

**承認の門は、規模で軽くしません。**設計の量は依頼の大きさで変えていいけれど、「これでいい」を待つことだけは、どんな小さな依頼でも省かない。これが、いちばん効きました。

## 5. ツールごとのやり方

### Claude Code

- **plan mode**：Shift+Tab で切り替えます。エージェントはファイルを読んで計画を立てますが、ファイルは書き換えません。計画を見て、良ければ通常のモードに戻して作らせます。「構造」の依頼は、ここから始めるのが安全です
- 計画は、そのまま受け取らずに直せます。気になる行は、その場で「ここは〜にして」と返してください <!-- 要確認：Ctrl+G で計画をエディタで開ける（公式 best-practices） -->
- 依頼文1〜5は、plan mode の最初のメッセージにそのまま使えます

### Codex・Cowork・ChatGPT など

仕組みの名前は違っても、やることは同じです。

- 最初のメッセージに、規模の宣言、着手前の3行、依頼文1を貼る
- 「私が『これでいい』と言うまで作らないで」を最後に付ける
- 長い作業を任せる前に、計画だけを先に出させる

## 6. 頼んでいないことを足させない規約

「思ってたのと違う」には、もう一つの形があります。頼んだものは合っているのに、頼んでいない機能や変更が混ざっている。エージェントは親切なので、良かれと思って足してきます。

悪意はありません。でも、確認する範囲が膨らみ、どれが事故の原因か追えなくなります。私の場合は「翻訳が無ければ原文を出す」という親切な逃げ道が、公開忘れを隠しました。

リポジトリの直下に `CLAUDE.md`（Codex なら `AGENTS.md`）として置きます。チャットなら、最初に貼ってください。

```markdown
## 頼み方の約束
- 依頼を受けたら、最初の行で規模を宣言する（調べる／限定／構造）。迷ったら重い方。
- 「構造」の依頼は、私が決めることを最大5つ挙げ、1つずつ質問する。
- 案は3つまで。各案に「狙い」「捨てたもの」「失敗する場面」を書く。
- 私が「これでいい」と言うまで作り始めない。設計が2文でも省かない。

## 範囲の約束
- 変更は、すべて依頼にたどれること。
- 頼まれていない改善・機能・抽象化は実装しない。思いついたら、最後に「提案」として書く。
- エラーを隠す逃げ道（失敗したら黙って別の値を使う処理）を、勝手に足さない。足すなら理由を書いて、私に聞く。
- 方針を変えたら、報告の最初の行で「方針を変えた」と言う。
```

Claude Code の公式ドキュメントも、CLAUDE.md は短く保つように勧めています。長くしすぎると、肝心の指示が守られなくなるからです。この規約も、あなたの作業に関係のない行は消して使ってください。

## 7. 実例：2つの頼み方

### 3Dの背景

**以前**
```
背景が真っ黒。もっと良くして。
```

**今なら**
```
廃墟の街の360°背景を作りたい。作り始める前に、私が決めないといけないことを重要な順に5つ挙げて。
```
→ 背景についてこう頼むと、「視点の高さ」「霧の量」「光源の色温度」「素材の密度」が並びます。当時の私はこれをせずに、6回作り直しました。

最後に効いたのは、依頼文3の形でした。明るさを優先した版（建物は見えるが、床が空っぽ）と、密度を優先した版（暗いが、物が詰まっている）。**2枚を並べて初めて、私が欲しかったのは明るさではなかったと分かりました。**最初からこの2つを比べていれば、6回はかからなかったはずです。

### 紹介動画

最初の指示は1文でした。エージェントは、作る前に「投稿先のアカウント」と「動画の見た目」の2問を、選択肢つきで聞いてきました。私が決めたのはこの2つだけで、残りは任せられました。

**人間が決めることは、実は少ないのです。**ただ、その少ないことを決めないまま任せると、整合はしているのに、誰の記憶にも残らないものが返ってきます。

創作の場合、私が決めるのは5つだけです。読後感、主人公の芯、世界の圧力、中心の関係、着地と規模。この5つが埋まっていれば、残りは任せられます。短編を書き終えた翌日に、フルボイスのゲームとして公開できたこともあります。速さは、手順を飛ばして出たものではなく、飛ばさなかったから出たものでした。

## 8. やりがちな失敗6つ

**1. 「おまかせで」と答える**
決めることの一覧をもらって、見ずに捨てています。一つでいいので、自分で選んでください。

**2. 5問にまとめて答える**
雑になります。1問ずつにしてもらいます。

**3. 案を5つ以上出させる**
選べなくなって、「おまかせで」に倒れます。3つまで。

**4. 小さい依頼だから、確認を省く**
事故は小さい依頼から起きます。確認は短くするだけで、省かない。

**5. 途中で方針が変わったのに、宣言し直させない**
「限定」で始めた作業が、途中で「構造」の大きさになることがあります。格上げを宣言させて、決めることを出し直させます。

**6. 1時間で出てきたものを、方向が違うのに直し続ける**
方向が違うなら、捨てて、決めることからやり直すほうが速いことが多いです。捨てにくいのは分かります。だから、捨てずに済むように、作る前に決めます。

## 最新メモ（2026年9月26日時点）

- Claude Code の公式ドキュメント（best-practices）は、「調べる → 計画 → 作る → コミット」の順を勧めている。調べる段階と計画は plan mode（Shift+Tab）でやる
- Claude Opus 5.5 は、既定の effort（考える量）が medium になった <!-- 要確認：whats-new ページ -->。構造の大きい依頼で計画が浅いと感じたら、effort を上げるか、plan mode で計画だけを先に出させる
- Opus 5.5 は「大事なことから先に書く」ように作り直された。決めることの一覧も、重要な順に並べてと頼むと素直に返ってくる

## この方法で言えないこと

- 記録は私ひとりのもので、比較実験はしていません
- 主に Claude Code で運用しています。依頼文と規約は平文なので他のエージェントでも使えますが、同じように効くかは確かめていません
- 「決めること5つ」の中身は、分野によって当たり外れがあります。外れたら、「他に決めるべきことはある？」と一度だけ聞き直してください

## 次回

作る前に決めても、できあがったものを少し直したくなることはあります。ところが「ここだけ直して」と頼むと、良かった所まで変わってしまう。直すたびに、別の所が壊れる。

なぜ一部だけ直すのは、こんなに難しいのか。次回は、修正地獄から抜ける方法を書きます。
