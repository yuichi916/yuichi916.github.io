## あなたが決める5スロット

ジャンルを問いません。**この5つが埋まれば書き出せます。**逆にどれかが空だと、その空欄に対応した壊れ方をします。

| # | スロット | 問い | 空欄だと起きること |
|---|---|---|---|
| 1 | **読後感** | 読み終えた人の胸に何が残ってほしい？ | 話は進むが、何のための話か分からなくなる |
| 2 | **主人公の芯** | 何を持っていて、**そのせいで**何を失う？ | 都合よく動く駒になり、感情移入されない |
| 3 | **世界の圧力** | この世界が主人公に強いていることは？ | 障害が場当たりになり、世界が書き割りになる |
| 4 | **中心の関係** | 誰との関係が物語を動かす？その**非対称**は？ | 出来事は起きるが、関係が変化しない |
| 5 | **着地と規模** | どこで終わる？全何話？ | 終われない。永遠に続く |

**全部一行で書きます。**長く書けたら、それは決定ではなく設定資料です。

**日常・青春**

```
世界の圧力: 期限 — 部活は今年の夏で終わる
中心の関係: 欲しいものをはっきり言う後輩。眩しくて、正視できない

```

**ミステリ**
```
読後感    : 犯人を憎めなくさせたい
主人公の芯: 細部を見逃さない / だから人の悪意まで見えてしまう
世界の圧力: 掟 — この島では、過去の事故に触れないことになっている
中心の関係: 唯一、彼に嘘をつく依頼人。信じたいのに検証してしまう
```

**今回の作品（SF）**


### コツ①「主人公の芯」は強みと代償を同じ行に

これが物語を自動で生む最小単位です。強みは能力でなくて構いません（立場・性格・過去・技能、何でも）。

```
◯ 何にでも合わせられる / だから自分の欲しいものが分からない
◯ 誰よりも早く走れる   / だから置いていく側にしかなれない
× 優しくて努力家       ← 代償が無い。ただの良い人で、物語が起きない
```

### コツ②「世界の圧力」は禁止だけじゃない

| 類型 | 形 | 例 |
|---|---|---|
| **禁止** | ◯◯してはいけない | 悲しむことが制度的に禁じられている |
| **欠乏** | ◯◯が足りない | 水が配給制で、家族の数で量が決まる |
| **期限** | ◯◯までしかない | 部活は今年の夏で終わる |
| **掟** | ◯◯ということになっている | この島では、過去の事故に触れない |

どれか1つで足ります。そして**世界観はここから派生させます**。設定を広く作り込もうとすると、いつまでも書き始められません。

```
圧力を1つ置く
 → 仕組み : それを維持しているのは何か
 → 例外者 : そこから外れている者は誰か   ← 主人公の居場所になる
 → 抜け道 : 破られている場所はどこか     ← 物語が動く場所
 → 執行者 : 信じて守らせている者は誰か   ← 敵役。悪人である必要はない
```

「期限 — 部活は今年の夏で終わる」に当てると、こうなります。

```
仕組み : 学校制度と大会日程
例外者 : 引退後も来てしまう三年   ← 主人公の居場所
抜け道 : 誰もいない朝の体育館     ← 関係が動く場所
執行者 : 進路を心配する顧問       ← 敵役だが、正しいことを言っている
```

> 📷 **画像: 10_pressure_derive.png**
> *圧力を1つ決めると、世界・主人公の居場所・舞台・敵が同時に決まる*


**世界・主人公の立ち位置・舞台・敵が同時に決まりました。**しかも矛盾しません。

### コツ③「中心の関係」は対等にしない

対等な二人は物語になりません。どちらかが、相手の持っていないものを持つ。恋愛でなくて構いません（相棒・師弟・敵・親子でも同じです）。

要は、**主人公の強みが通用しない唯一の相手**を置くと、それだけで関係が物語になります。

## 5行の次にやること — 設定資料集を育てる

5行は**決定**です。ここから、そこに乗る**合意事項**を作ります。世界観、ストーリーの指針、キャラ設定。いわゆる設定資料集です。

**自分で書いてもいいし、AIと壁打ちして固めてもいい**です。決定権さえ手放さなければ、どちらでも同じところに着きます。

これを作らないと、後半で必ず矛盾します。AIが執筆中に参照する唯一の正典になるからです。

### 目次は固定する（これ以上増やさない）

| 章 | 中身 |
|---|---|
| 1 世界 | 圧力とその仕組み / 地理と階層 / 時代と技術水準 / 禁忌と例外 |
| 2 用語 | 固有名詞の一覧と表記の統一 |
| 3 人物 | 主要3人 + 脇役。1人1枚 |
| 4 物語の指針 | 人称・時制・文体 / **やらないこと** |
| 5 話数構成 | 各話の役割を1行ずつ |
| 6 年表 | **作中で言及される過去の出来事だけ** |

**分量の上限は「本編に出ない設定は書かない」。**書きたくなったら、断章や作中の書物として本編に出す形にします。出せないなら、それは要らない設定です。

### 用語表がいちばん事故を防ぐ

意外かもしれませんが、AI執筆で最も頻発する破綻は世界観ではなく**表記ゆれ**です。

「アビス／深淵」「五一七／517」「監督官／管理官」が混在すると、検索も改稿も効かなくなります。正式表記・読み・初出話をただの表にしておくだけで、これが消えます。

### キャラシートは1人1枚

```
一行紹介   : 試験に14回落ち続けている男
話し方の癖 : 語尾を飲み込む
身体の癖   : 無意識に右手で空をなぞる     ← 感情を説明せず、身体に宿す
隠した一面 : 誰も見ていない所で配給を差し入れている
呼び方     : 主人公→「あんた」 / ヒロイン→「お嬢ちゃん」
```

- **身体化した癖**を1つ入れておくと強いです。全編で反復して、誰かがそれを見抜く瞬間が山場になります
- **呼び方の表**は地味ですが効きます。同じ人物でも呼ぶ相手で温度が変わって、人間関係が立体になります

### 「やらないこと」を書く

指針は「やること」より**「やらないこと」**のほうが効きます。そのままAIへの制約になるからです。

```
やらない: 説明台詞で世界設定を語らせない
やらない: 主人公に自分の感情を言語化させない（身体と行動で出す）
やらない: 章末を疑問形で終わらせない
```

### 壁打ちの型

AIと固めるときは、頼み方で結果がまるで変わります。

| 目的 | 頼み方 | 注意 |
|---|---|---|
| **選択肢を出させる** | 「◯◯の案を5つ、方向性を変えて」 | **選ぶのは自分**。採用理由を一行残す |
| **矛盾を突かせる** | 「この設定で破綻する場面を挙げて」 | いちばん費用対効果が高い |
| **尋問させる** | 「作者に質問して。答えないと書けない順に」 | 自分の空欄が可視化されます |
| **平凡さを検出させる** | 「この設定でありがちな展開を10個」 | 出たものを**避ける**ために使う |

**やってはいけないのは「いい感じにして」「膨らませて」**です。整合はするけれど、誰の作品でもないものが出てきます。

壁打ちは選択肢を増やす道具であって、決定を代行させる道具ではありません。ここを間違えると、5行を決めた意味が消えます。

### 止め時

次の3つが埋まったら終わりにします。**それ以上は本文を書きながら足す。**

1. 用語表が埋まっている
2. 主要3人の呼び方の表が埋まっている
3. 各話の役割が1行ずつ書けている

## Claude Codeに任せたこと

- **各話の配分と配置表** — 何話目でどの伏線が現れるか
- **脇役の設計・名前・見せ場**、地名・組織名・専門用語
- **地の文と会話の執筆**、文体の統一
- **伏線の敷設と回収の管理**
- 台本への変換、エンジンの実装、画像・音声の生成、検証、公開

**5スロットが埋まっていれば、残りは整合性の問題**なので任せられます。逆に曖昧なまま丸投げすると、**整合はしているのに心に残らないもの**が出てきます。ここが分かれ目でした。

## 実際にどう形になっていったか

### 小説になるまで

配置表を先に作らせます。「第N話でフックがどう現れるか」を全話ぶん表にしてもらう。

**表の段階なら、破綻は1行直せば消えます。**本文を書いてから気づくと、1話まるごと消すことになります。ここを飛ばすと後で高くつきました。

あとは1話ずつ書いてもらいます。**1話 = 1ファイル**（`ep01.md` …）にすると、直すときの影響範囲が目で追えます。そして**完結させてから推敲**。未完のまま推敲に入ると永遠に終わりません。

> 📷 **画像: 11_novel_files.png**
> *1話1ファイル。合計13.9万字*


### ゲームになるまで

ここが一番「へえ」と思ったところです。

小説の地の文と会話は構造が決まっているので、**ゲームの台本への一次変換はスクリプトで機械的にできます**。

```js
window.SEIKAI_SCRIPT = { ep1: { scenes:[
  { bg:'slumA', bgm:'under', beats:[
    {say:'della', text:'「目つきが気に入らねえ」'},
    {say:'kai',   text:'「了解」', ex:''},
    {show:'kai', pos:'right'},
    {say:'potz',  text:'「毎朝毎朝、よく耐えるな」'},
    {say:'narr',  text:'隣の奴隷——五一八番のポッツが小声で言った。'},
  ]},
]}};
```

> 📷 **画像: 05_novel_to_game.png**
> *同じ場面が、小説 → 台本データ → ゲーム画面と変わっていく*

`「…」` を台詞ビートに、場面転換を背景切替に、心内描写を内心フラグ付きの台詞に落とす。**台本はただのデータで、エンジンはそれを再生するだけ**にしておくと、エンジンに触らずに物語を増やせます。

小説が完結していたので、**着手から4時間半で全15話がブラウザで動きました。**

ElevenLabs で、**主役2人だけ**フルボイスにしました。

予算ではなく**容量の問題**です。全キャラに付けると500MBを超えて置ける場所がなくなります。主役2人なら200MB程度。しかも2人だけが喋ると「**この2人の物語なんだ**」と伝わって、演出としてもよかったです。

## どこまで自分でやるべきか

やってみた実感として、線はここでした。

**自分でやる**
- 5スロットを埋める
- 設定資料集の決定に責任を持つ（壁打ちの相手はAIでいい）
- 配置表にOKを出す
- 書き上がった小説を**読む**（ここは代替できません）

**渡していい**
- それ以外の全部

小説を読み返す作業だけは残ります。というより、**そこが唯一の楽しみ**でもありました。自分が決めた5行から、読んだことのない物語が出てくるので。

## まとめ

用意したのは5行でした。

読後感、主人公の芯、世界の圧力、中心の関係、着地と規模。

そこから先は、配置表も本文もエンジンもボイスも背景もOPも、全部渡せました。

**AIができることが増えたぶん、人間が決めるべきことの解像度が上がった**という感じです。楽にはなっていません。5行の質が、そのまま作品の質になります。

---

ここまでが「何を決めて、何を渡したか」の話でした。

5行を決めるところまでは、ここまでで足ります。問題はその先です。

台本化で話者がずれる。素材が増えて管理できなくなる。ボイスがエラーも出さずに無音になる。完成しても容量が大きすぎてどこにも置けない。**この4つは、ほぼ全員が同じ場所で詰まります。**

以下は、そこを通り抜けるための**ノウハウ集**です。工程の順番、各ツールの**実測パラメータ**（Stable Diffusion / Blender / ElevenLabs の設定値そのもの）、エンジンの設計、公開の構成、そして**時間が足りないときにどこから削るか**。調べ直さずに着手できる状態にしてあります。

なお後半は、GitHub Pages や生成AIツールを自分で触る前提で書いています。コードが書けなくても読めますが、完全な初心者向けではありません。

## 1. 売れる形を先に決める

### ブラウザ完結にする — これが最大の武器

インストール不要・アカウント不要・**リンクを開けば読み始められる**。投稿サイト・SNS・ブログ、すべての流入経路がそのまま入口になる。ダウンロードを挟む形式とは、この一点だけで初速が桁違いになる。

### 容量が普及範囲を決める

| 構成 | 容量 | 置ける場所 |
|---|---|---|
| ボイスなし | 〜30MB | ほぼ全部 |
| 主役2人フルボイス | 150〜250MB | 自前ホスティング / リンク掲載型 |
| 全キャラフルボイス | 500MB〜 | 実質どこにも置けない |

→ **ボイスは主役2人だけ**が費用対効果の最適点。脇役は無音でも違和感が出ない（むしろ主役2人だけが喋ると「この2人の物語」だと伝わる）。

### 尺と構成の型

- **全15話 / 1話あたり8,000〜10,000字 / 総プレイ3〜4時間**が扱いやすい
- 部構成は `第一部(ep1-5)＝閉じた場所からの脱出` → `第二部(ep6-15)＝広い世界と正体`
- **分岐は最終話だけ**。途中の選択肢は必ず合流させ、演出差分にする

### 置き場所は GitHub Pages。ビルドを持たない

**ビルド工程を作らない**のが最短化の本体。静的HTMLをpushするだけで公開される。

```
リポジトリ直下
  index.html / game.html / ...     ← ルートに置いたHTMLがそのままURLになる
  assets/<作品>/                    ← 画像・音声・台本js
  .nojekyll                        ← 空ファイル。1個だけ必須
```

- **`.nojekyll` を必ず置く**。無いと Jekyll が走り、`_` 始まりのディレクトリが配信されない・ビルド待ちが挟まる。空ファイルを1つ置くだけで全部止まる
- `package.json` も `_config.yml` も要らない。**バンドラを入れた瞬間に「デプロイ＝ビルド＋確認」になり、反復速度が落ちる**
- ライブラリはCDNから読む（three.js等）。npm依存を持ち込まない
- 公開は `git push` のみ。反映は数十秒〜数分

**Node.jsはビルドではなく検査に使う**。大型の単一HTMLは壊れても画面が出ないので、commit前に構文を通す:

```bash
node --check extracted_inline_script.js   # importmap の JSON は FAIL で正常
```

ローカル確認は `python -m http.server 8000`（`file://` だと fetch と CORS が効かず、実環境と挙動が変わる）。

**容量**: GitHub のリポジトリは1GB程度が実用上限、単一ファイルは100MB。フルボイス200MB級は収まるが、これ以上増やすなら音声は外部ホストへ逃がす。

> 📷 **画像: 14_repo_layout.png**
> *ビルド工程が無いので、公開は push するだけになる*


### 題材の選び方（需要の採掘）

あらすじではなく**なろう系の長文タイトルを数万件regex集計**する。長文タイトルは展開そのものの記述なので情報量が桁違い。実測で出た太い鉱脈: 悪役令嬢 / 実は正体 / 追放 / 喪失と再会 / 死に戻り / 勘違い / 余命。

**全部入れない**（テンプレ化する）。未回収の鉱脈を1〜2本だけ、しかも**逆側の視点**で使う（「追放」→ 追放される側でなく**見送る側**）。

## 2. 中核フックと配置表

### フックは2つ、「上書き層」として設計する

片方を**世界の仕掛け**（登場人物に起きている異常＝読者が推理できる）、もう片方を**語りの仕掛け**（語り手の側の仕掛け＝終盤で気づく）にすると干渉しない。

そして**既存プロットを書き直さない**。維持と追加を分けて宣言する:

```
1. 既存のプロット（第一部の結末）は維持
2. フックを上書き層として追加
3. 各話の末尾に数行、別の層の語りを挿入
4. 最終話でその層を回収する
5. ヒロインの台詞に「兆候」を散りばめる
```

この5行があると改稿が**差分作業**になる。全話書き直しは数日では終わらない。

### キャラ配置の型（3人で立つ）

| 役 | 汎用の原則 | 能力もの | ミステリ | 日常 |
|---|---|---|---|---|
| 主人公 | 強みと代償を1つずつ持つ | 能力＝呪い | 観察眼＝人間不信 | 協調性＝自我の希薄 |
| 相手役 | 主人公の強みが**通用しない**唯一 | 能力が効かない | 唯一嘘をつく相手 | 欲望を言語化できる |
| 敵役 | 主人公と**同型の傷**を持つ | 同じ能力で失敗した先例 | 同じ動機の別解 | 同じ迷いの果ての大人 |

敵役を「鏡像」にすると、以後の敵の全言動が再文脈化されて強くなる。

### 書き始める前に固定するもの

- **全話ぶんの配置表**。表なら破綻が1行で直る
- ナレーションの人称と時制
- 主要キャラの口癖と、**その口癖が後半で帯びる第二の意味**（費用対効果が最も高い）

## 3. エンジンと台本変換（半日）

### 台本はデータ、エンジンはコード

話ごとに別ファイルで後読みする。**エンジンを触らずに物語を増やせる形**にする。

### ビート実行の1原則

```js
const b = cur.beats[cur.i++];
if(b.bg){ setBG(b.bg); continue; }       // 画面を止めない
if(b.say!=null){ renderSay(b); return; } // 描画で止まる
```

`bg/bgm/se/show` は `continue`、`say/choose/wait` は `return`。**この一貫性が崩れると進行不能バグ**になる。ここだけは厳格に。

### 小説 → 台本の一次変換は機械にやらせる

- `「…」` → `say` ビート（話者は直前の地の文から推定）
- 場面転換記号 → `bg` / `bgm` ビート
- 心内描写 → 内心フラグ付き `say`（後でTTSの `[whispers]` に対応させる）

**話者の自動推定を信用しない**。間違えるとボイスの声が変わり、プレイした瞬間にバレる。推定できなかった行は「未確定」として残し、人間が埋める。

### 最小構成で先に通す

セーブ・オート・スキップ・章選択の4つだけ入れれば作品として成立する。ミニゲーム・探索・コレクションは後付けでよい（**全部スキップ可にする**）。

## 5. 背景

### 速攻ルート: Stable Diffusion（半日）

```python
{"width":1344, "height":768, "steps":30, "cfg_scale":5.0,
 "sampler_name":"DPM++ 2M SDE", "scheduler":"Karras"}
```

シーンごとに**seed固定**で。同じ場所の再訪カットは同seed＋プロンプト微差にすると「同じ場所」に見える。**まずこれで全話通す。**

### 本気ルート: Blender 360°パノラマ（3日）

差別化が要るならここ。KitBash3D等のアセットを equirect で焼く。

```python
sc.render.engine = 'CYCLES'
sc.render.resolution_x, sc.render.resolution_y = 2560, 1280   # equirect は 2:1
sc.cycles.samples = 150
sc.cycles.use_denoising = True
sc.cycles.time_limit = 200        # ショット毎に打ち切って保存（ハング対策）
sc.view_settings.view_transform = 'AgX'
cam.data.type = 'PANO'
cam.data.cycles.panorama_type = 'EQUIRECTANGULAR'   # 4.x は cam.data.panorama_type
```

- **ボリュームフォグを使わない**。equirect のレイマーチで固まる（実測2.5時間凍結）
- **配置は bounding box 基準**。KitBash系はメッシュ原点とジオメトリがズレていて、座標直指定だとクローンが元の都市座標に飛ぶ
- **地の底のレシピ**: 露出 -0.6 / world強度 0.04 / 低い黒天井 + 頭上を配管で塞ぐ / 床を工業ガラクタで充填 / 床材は暗い濡れ路面。明るいコンクリ床 + 低カメラは白飛びする
- **屋外が曇天に見えたら**: 空の強度を 1.0→**0.35**（AgXは高輝度を無彩色へ寄せる）、太陽をカメラ背後へ、`dust_density` 2.0→0.30、`sun_elevation` を44°程度に上げる

three.js の球体に貼れば**視点を動かせる探索パート**になり、体験の格が上がる。

## 6. ボイス（1日。生成は放置でよい）

ElevenLabs v3。**主役2人だけ**。

```python
{"model_id": "eleven_v3", "language_code": "ja", "voice_settings": VS[who]}

VS = {  # 少年は低stabilityで感情の振れ幅、少女は高stabilityで安定
  'kai': {"stability":0.35, "similarity_boost":0.88, "style":0.00, "use_speaker_boost":True},
  'rin': {"stability":0.68, "similarity_boost":0.72, "style":0.12, "use_speaker_boost":True},
}
```

### 3つだけ守れば事故らない

**1. タグは短いオーディオタグ1個まで**（`[whispers]` `[sad]` `[nervous]` `[surprised]`）。長い説明列は**読み上げられる**。実測で心内台詞33本の頭に英語が数秒混入した。

**2. ファイル名は台詞のハッシュにする**が、**改稿のたびに棚卸し**（欠落0 / 孤児0）。1文字直すと参照先が変わって無音になり、エラーは出ない。実測で161本が全部無音になっていた。

```python
def key_of(t):
    h = 0
    for ch in t:
        h = (h*31 + ord(ch)) & 0xFFFFFFFF
        if h >= 0x80000000: h -= 0x100000000
    return 'k' + str(h)
```

**3. 固有の読みは送信文字列だけ仮名化**する。ファイル名は原文ハッシュのままなので参照は壊れない。同じ漢字の読み違いは書き起こし比較では**原理的に検出できない**（書き起こしが音を漢字に正規化して返すため）。仮名を強制するには、書き起こしモデルの語彙から漢字を含むトークンを禁止する。

```python
tok = model.hf_tokenizer
kj = re.compile(r'[一-鿿]')
sup = [-1] + [i for i in range(tok.get_vocab_size()) if kj.search(tok.decode([i]))]
segs, _ = model.transcribe(path, language="ja", beam_size=5, suppress_tokens=sup)
```

生成は数時間かかるので**寝る前に回す**。レジューム前提で書く。

## 8. OP映像（2日）

**動画編集ソフトは要らない。**HTMLを時間駆動レンダラーにして1フレームずつ書き出す。

```js
window.__setTime = (t) => { /* 任意時刻の状態を完全再現 */ };
```

- 全演出を **`t` の純関数**にする。CSS transition や rAF の積分に依存させるとキャプチャでズレる
- **カット割りは楽曲の拍に打つ**。境界を先に確定し、以後は中身だけ改善する
- 90秒 / 30fps / 30〜40カットが標準的な規模
- Playwright で `__setTime(t)` → screenshot → ffmpeg で結合
- **完成画は本編のイベントCGに転用できる**（カラーグレード込みなので生の3Dより遥かに使える）

## 11. 各工程の「完了」を観測で定義する

活動ではなく**観測できる結果**で完了とする。ここを曖昧にすると「だいたいできた」が積み上がって、最後に破綻する。

| 工程 | 完了の観測 |
|---|---|
| 企画 | 配置表が全話埋まっている |
| 小説 | 最終話の最後の行がある |
| 台本 | 実プレイで最終話に到達できる |
| 立ち絵 | 全 `show` キーが実在ファイルを指す |
| 背景 | 全 `bg` キーが実在ファイルを指す |
| ボイス | 欠落0 / 孤児0 |
| 音楽 | 全 `bgm` キーが実在する |
| OP | 黒フレーム0 / `ffmpeg -f null -` が無出力 / 尺が設計どおり |
| 公開 | **ライブURLを叩いて期待の中身が返る** |
