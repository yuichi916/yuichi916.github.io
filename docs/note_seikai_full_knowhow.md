# 第1章 プロットと世界観 —— 書き始める前に勝負がつく

小説を数日で書き切れるかどうかは、**1文字も書く前の設計**で決まります。

## 中核フックは2つ用意して統合する

フック1つだと中盤が持ちません。3つ以上だと読者が追えません。**2つ**がちょうどいい。

そのうえで、片方を**世界の仕掛け**、もう片方を**語りの仕掛け**にすると、互いに干渉しません。

- **世界の仕掛け** = 登場人物の身に起きている異常。読者が途中で推理できる
- **語りの仕掛け** = 語り手の側に置く仕掛け。読者が終盤で気づく

この2層構造だと、片方を追いかけている読者がもう片方に不意打ちされます。

## フックは「上書き層」として設計する

ここが一番実用的なコツです。

既存のプロットを書き直してはいけません。**維持するものと足すものを分けて宣言する**。私のマスタープランには、こういう形の5行が書いてありました。

```
1. 既存のプロット（第1部の結末）は維持
2. フックB+Cを上書き層として追加
3. 各話の末尾に数行、別の層の語りを挿入
4. 最終話でその層を回収する
5. ヒロインの台詞に「兆候」を散りばめる
```

この5行があるおかげで、改稿が**差分作業**になりました。全話書き直しは数日では絶対に終わりません。

## 配置表を先に作る

「第N話でフックがどう現れるか」を、**全話ぶん表にしてから本文を書きます**。

表の段階なら、破綻は1行直せば消えます。本文を書いてから気づくと、1話まるごと消すことになります。私は15話ぶんの配置表を作ってから書き始めました。

## 文体規則を先に固定する

後から統一しようとすると全文を読み直す羽目になります。着手前に決めます。

- ナレーションの人称と時制
- 別時制パートの人称
- 主要キャラの口癖と、**その口癖が途中で帯びる第二の意味**

最後のやつが一番効きます。初出時は何気ない口癖として置いて、後半で意味が反転する。読者は「一度目から仕掛けられていた」と気づきます。

## 需要は「あらすじ」ではなくタイトルから採掘する

これは変わったやり方かもしれません。

手元の蔵書データベースから、**なろう系の長文タイトルを数万件、正規表現で頻度集計**しました。あの長いタイトルは、実は**展開そのものの記述**なので、あらすじより遥かに情報量があります。

出てきた鉱脈: 悪役令嬢 / 実は正体 / 追放・見送る側 / 喪失と再会 / 死に戻り / 勘違い・周囲だけ知ってた / 余命。

ここで大事なのは、**全部入れないこと**。全部入れるとテンプレになります。自作の実装状況と突き合わせて、**未回収の太い鉱脈だけ**を注入します。

そして頻出型は**逆側の視点**で使います。「追放」が106件ヒットしたとき、私が書いたのは追放される側ではなく、**見送る側**の一言でした。

# 第2章 小説を書く

書き方の技術論は長くなるので要点だけ。運用のほうが大事です。

- **1話 = 1ファイル**にする。話をまたぐ改稿の影響範囲が目で追える
- **完結させてから改稿する**。未完のまま推敲に入ると永遠に終わりません
- 改稿は**診断してから注入する**。感覚で書き直さない

「診断」というのは、章ごとの選択肢数・演出数・章末の落ちの型を**機械集計する**ということです。平坦に感じる章には必ず構造的な理由があります。感覚で書き直すと、良かった場面まで壊します。

集計で一番効いたのは**重複検出**でした。2章連続で同じ場所を訪れている、みたいなやつです。これは飽きの最大要因なんですが、書いている本人は気づけません。

そして重複は**削除ではなくエコー構造に作り替えます**。一度目は崩れる場面、二度目は自分の声で読み直す場面にする。同じ場所が二度出てくることが、逆に武器になります。

# 第3章 小説 → サウンドノベル台本

ここからがゲーム化です。

## 台本はデータ、エンジンはコード

これが全部の前提です。

```js
window.SEIKAI_SCRIPT = { ep1: { scenes:[
  { bg:'slumA', bgm:'under', beats:[
    {say:'della', text:'「目つきが気に入らねえ」'},
    {say:'kai',   text:'「了解」', ex:''},
    {show:'kai', pos:'right'},
    {say:'potz',  text:'「毎朝毎朝、よく耐えるな」'},
    {say:'narr',  text:'隣の奴隷——五一八番のポッツが小声で言った。'},
  ]},
]}};
```

台本を素のJavaScriptデータにして、話ごとに別ファイルで後から読み込みます。こうすると**エンジンに一切触らずに物語を増やせます**。

## 変換は機械にやらせて、演出だけ人が足す

小説の地の文と会話は構造が決まっているので、一次変換はスクリプトで十分です。

- `「…」` の連続 → `say` ビート
- 場面転換の記号 → `bg` / `bgm` ビート
- 心内描写 → 内心フラグ付きの `say`

ただし**話者の自動推定を信用してはいけません**。話者を間違えるとボイスの声が変わるので、プレイした瞬間にバレます。推定できなかった行は必ず「未確定」として残して、人間が埋めます。

## 止まる命令と止まらない命令を分ける

エンジン側の設計で一番大事なところです。

`bg` / `bgm` / `se` / `show` は画面を止めない（`continue`）。`say` / `choose` / `wait` は止まる（`return`）。

この一貫性が崩れると**進行不能バグ**になります。ここだけは規則を厳格に守ります。

## 分岐は最終話だけ

選択肢は必ず合流させて、**演出の差分だけ**にします。15話ぶんの分岐を個人で保守するのは不可能です。

ただしそれだと選択が軽くなるので、**「選択の記憶」**を入れました。優しい選択に不可視のフラグを積んでおいて、**最終話の一行だけを変える**。分岐エンドより「ずっと見ていてくれた」感が出ます。

# 第4章 フルボイス化 —— ここが地雷原

正直に言うと、**この工程で一番時間を溶かしました**。TTSは「音声が出る」ところまでは10分で行きますが、そこから先が本番です。

このジャンルの不具合は**クラッシュしません**。ボイスが鳴らない、背景が出ない、断章が消える。どれもエラーを出さずに静かに劣化します。

## 事故1: 改稿したら161本が無音になった

ボイスファイルの名前を、台詞テキストのハッシュで決めていました。

```js
function keyOf(t){ let h=0; for(let i=0;i<t.length;i++){ h=(h*31+t.charCodeAt(i))|0; } return 'k'+h; }
```

つまり**台本を1文字直すと参照先が変わって、その台詞は無音になります**。エラーは出ません。

改稿で足した心内描写161件が、全部無音になっていました。プレイして初めて気づきます。

**対策**: Python側で同じハッシュを再現して、台詞を全抽出 → 期待ファイル名を算出 → **欠落0 / 孤児0** を確認する棚卸しを、改稿のたびに回すようにしました。

```python
def key_of(t):
    h = 0
    for ch in t:
        h = (h*31 + ord(ch)) & 0xFFFFFFFF
        if h >= 0x80000000: h -= 0x100000000
    return 'k' + str(h)
```

## 事故2: 演技指示が読み上げられた

ElevenLabs v3 に、こういう指示を渡していました。

```
[a twelve year old boy, boyish and light, inner monologue, hushed, pained, holding back tears]
```

これが**演技指示ではなく読み上げ対象**になりました。心内台詞33本の頭に、英語が数秒混入していました。

**対策**: タグは**短いオーディオタグ1個まで**（`[whispers]` `[sad]` `[nervous]` `[surprised]`）。

## 事故3: 漢字の読み間違いは、文字比較では原理的に見つからない

これが一番厄介でした。

作中の中核語である「**空**」が、「**そら**」ではなく別の読みで発音されていました。「空って、こういう青なんだ」という台詞が、まったく違う音で鳴っていた。

問題は、**書き起こしで検証しても絶対に見つからない**ことです。書き起こしは音を漢字に正規化して返すので、どう読んでも同じ「空」と出てきます。同じ漢字の読み違いは、文字列比較では原理的に検出不可能です。

**対策**: 書き起こしモデルの語彙から、**漢字を含むトークンを全部禁止**して仮名を強制しました。

```python
tok = model.hf_tokenizer
kj = re.compile(r'[一-鿿]')
sup = [-1] + [i for i in range(tok.get_vocab_size()) if kj.search(tok.decode([i]))]
segs,_ = model.transcribe(path, language="ja", beam_size=5, suppress_tokens=sup)
```

`initial_prompt` で「ひらがなだけで書きます」と頼むだけだと、仮名で返るのは**29%**でした。トークン禁止でほぼ確実になります。

そして修正するときは、**TTSに送る文字列だけ仮名に置換**します。ファイル名は原文のハッシュのままなので参照は壊れません。ただし別読みの語を先に退避しないと事故ります。

```python
GUARD = [("空っぽ","\x01"),("空白","\x02"),("空気","\x03"),("空腹","\x04"),("空間","\x05")]
```

これを忘れると「そら間」「腹をそらかせ」になります。実際になりました。

## 事故4: 破損検出は「秒÷字数」ではダメ

途中で切れた音声を見つけるために尺を見ますが、**比率でやると1〜2文字の台詞が上位を独占**して本物が埋もれます。

さらに、**話者ごとに話速が違います**。

```
カイ: 秒数 ≈ 0.68 + 0.196 × 字数
リーン: 秒数 ≈ 0.90 + 0.228 × 字数
```

**話者別に回帰を引いて、その残差を見る**。尺だけだと偽陽性が65件出ましたが、「残差 > 2.5秒」と「書き起こしの一致率 < 62%」の両方を課したら10件まで落ちました。

## 事故5 —— 一番の失敗。98本の語尾を破壊した

ある台詞の末尾に、台本にない「で」という音が入っていました。

調べると「発話 → 1.25秒の無音 → 短い発話」というパターンでした。同じパターンのファイルを検索したら98本ヒットしたので、**一括で末尾を切りました**。

**これが致命的な間違いでした。**

「発話 → 無音 → 短い発話」は、**同時に「最後の一言の前の劇的な間」の形でもあった**んです。

- 「……わかる。（間）**でも——**」
- 「（間）**いるの**」
- 「（間）**決める**」

これが全部消えました。演技として一番いいところだけを、機械的に切り落としていたわけです。

幸いバックアップを取っていたので98本全部復旧できました。そのあと内容ベースの検出も2回試しましたが、どちらも偽陽性だらけで、**最終的に人間が確かめた1本だけ**を直しました。

ここから得た教訓が、この記事で一番伝えたいことです。

> **パターンが一致した = 不良、ではない。内容で確かめるまでは候補にすぎない。**
> **検証は適用の「後」ではなく「前」に置く。**

# 第5章 背景と立ち絵

## 360°パノラマは Blender で焼く

KitBash3D の3Dアセットを Blender でレンダリングして、equirectangular の全天球画像にしています。地下の廃墟も地上の城郭都市も全部これです。

**ハマった点**:

- **equirect × ボリュームフォグでハングします**。全天球のレイマーチで2.5時間凍結しました。ボリュームを使わず、ショットごとに時間制限で打ち切って保存する形にしたら各11〜15秒で終わりました
- **KitBash系はメッシュ原点とジオメトリがズレています**。座標を直接指定するとクローンが元の都市座標に出現して、床が空っぽになります。必ず bounding box 基準で配置します
- **地の底の絵作りのレシピ**: 露出 -0.6 / world強度 0.04 / 低い黒天井＋頭上を配管で塞ぐ / 床を工業ガラクタで埋める / 床材は暗い濡れ路面。明るいコンクリ床＋低いカメラは白飛びして構図が崩れます

## 立ち絵の切り抜き

**rembg は白い服 × 白い背景で穴を開けます**。`binary_fill_holes` と内側3pxの収縮で補修しました。暗い服でも同様に開きます。

あと生成時に「anime style, flat color」を入れると薄線フラット画風になって、他のキャラと画風が乖離します。プロンプトは揃えます。

## 立ち絵を動かす

ここは最近やった作業です。静止PNGの立ち絵に、呼吸とスウェイだけつけても「動いている」とは見えません。**髪と裾が動くかどうか**が分かれ目でした。

まず、**画像から動画を生成するAI（I2V）はこの用途に向きませんでした**。RTX 4070 / 12GB で Wan2.2 I2V は1ステップ18分。実用外です。

次に HyperFrames（HeyGen が公開しているHTML→MP4のOSS）を試しましたが、これも効きませんでした。高機能なんですが、宣言的に動かせるのが `opacity, x, y, scale, rotation` などの transform 系だけで、**すでにやっていることと同じ範囲**だったからです。カタログの50以上のブロックにも、キャラクターモーション系は1つもありませんでした。

結局、**平面のPNGを1枚の格子として歪ませるWebGLシェーダ**を自分で書きました。レイヤー分割も切り抜きも要りません。

```glsl
float ex   = abs(v.x-0.5);
float hair = smoothstep(0.48,0.02,v.y) * smoothstep(0.065,0.170,ex);
float dx   = 0.0220*hair*sin(t*1.32+sd+v.y*7.5)
           + 0.0100*hair*sin(t*2.45+sd*1.7+v.y*13.0);
gl_FragColor = texture2D(tx, v + vec2(dx, ...));
```

設計の勘所は3つです。

- **顔の中心を保護する**。中心±6.5%を不変形にしないと、アニメ顔は即座に崩れます
- **位相を高さでずらす**（`v.y*7.5`）。これが「毛先が遅れて追ってくる」正体です
- **接地点はピン留めする**。足元が動くと浮きます

検証は、**同じ時刻で振幅0と振幅1を描いて差分を取る**とキレイに分離できます。背景が同一なので、差分の帯の幅がそのまま「輪郭が動いたピクセル数」になります。実測で中央値5px、最大42pxでした。

# 第6章 OP映像を動画編集ソフトなしで作る

**[▶ OP映像（92秒）](https://www.youtube.com/watch?v=AYpOA6ArBCg)**

動画編集ソフトは使っていません。**HTMLを1フレームずつ書き出して**組み上げています。

## 原則: 全部を時間の純関数にする

```js
window.__setTime = (t) => { /* 任意時刻の状態を完全再現 */ };
```

CSS transition や requestAnimationFrame の積分に依存させると、キャプチャで必ずズレます。全ての演出を `t` の関数として書いて、Playwright で `__setTime(t)` を呼んでスクリーンショットを撮る。92秒 × 30fps = 2,760枚。それを ffmpeg でつなぎます。

## 事故: 2,760枚のうち96枚が真っ黒だった

元画像は健全なのに、書き出したフレームだけ黒い。

原因は、CSS `background-image` のラスタライズがスクリーンショットに間に合わず、**まだ何も描かれていない状態が撮れていた**ことでした。

**対策**: canvas に同期的に `drawImage` する。**画像が未デコードなら「描かない」**——そうすると前のフレームの絵が残るので、黒くなりません。プリロード時に `decode()` まで済ませてキャッシュしておき、キャプチャ側でも「そのフレームに必要な画像が載っているか」をゲートします。これで96枚→6枚になりました（残り6枚はカット転換の正当な暗転）。

## BGMのダッキングは包絡線で

台詞のとき音楽を下げる処理を、最初は区間指定でやっていました。

```
volume=enable='between(t,a,b)':volume=0.4
```

これは**階段状に切り替わるので明確に不自然**です。傾斜を作ります。

```python
FIN, FOUT, DEPTH = 0.55, 1.10, 0.58   # 下げ0.55秒 / 戻し1.10秒
def _env(a,b): return f"clip(min((t-{a-FIN:.3f})/{FIN},({b+FOUT:.3f}-t)/{FOUT}),0,1)"
```

さらに**近接した窓は先に統合します**。でないと「下げ→戻し→また下げ」でポンピングします。

検証は耳ではなくPCMで。フィルタの有無で同じ区間のRMS比を取れば、減衰量の傾斜がそのまま数字で出ます。

## OPの完成画は本編で再利用できる

OPの絵は**カラーグレード（空レイヤー・ヴィネット・ゴッドレイ）が乗った状態**なので、生の3Dレンダリングより遥かに使えます。本編のイベントCGは、OPレンダラーを `__setTime(t)` で止めて、文字系UIを消してから撮っています。

# 第7章 公開してわかったこと

## フルボイスは容量が跳ねる

合計208MBです（ボイス110MB / BGM 41MB / 画像54MB）。アップロード型のゲーム投稿サイトには容量上限があるので、**リンク掲載で済むサイトを先に**当たったほうがいいです。

## 完全オリジナルは初速が出ない

これは正直しんどいところです。知られていない世界観の作品は、告知しても最初の数十人が来ません。

現時点で一番費用対効果が高いと判断しているのは、**小説投稿サイトに原作を連載して読者プールを借りる**ことです。各話の末尾に固定でプレイ版へのリンクを置きます（最終話だけに置くと、途中で離脱した人に届きません）。

## 一番間抜けだった話

**最大の作品が、トップページから1本もリンクされていませんでした。**

しかも長期間。OGP も canonical も設定して、SEO を頑張っているつもりでいたのに、内部リンクが無ければクロールもされません。作ることに集中していると、こういう基本が抜けます。

# まとめ —— 一番大事だったこと

技術的な話をたくさん書きましたが、通して一番効いた原則は3つです。

**1. 順番を守る。** 小説を完結させてからゲーム化する。物語とコードの不確定性を同時に抱えない。

**2. 設計を先に、差分で作る。** 中核フックを2つ、上書き層として、配置表を作ってから書く。全話書き直しは数日では終わらない。

**3. 検証は適用の前に置く。** これが98本の語尾を壊して学んだことです。パターンが一致しただけでは、それは候補であって不良ではありません。機械的な一括処理は、必ずバックアップとセットで、少数を人間が確かめてから広げる。
