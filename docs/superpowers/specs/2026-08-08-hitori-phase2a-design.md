## 1. なぜこれをやるのか

利用者の評価は「まだあまい」。妥当である。現状は探せるようになったが、見た目が地味で、施設名では探せない。

見た目が地味だった原因は、写真が1枚も無いという制約を受け入れて、無難な一覧に逃げたことにある。**写真は無いが、幾何と数字はある。** 周辺施設の分布、最寄同業態までの距離、3軸のスコア — これらは他所から持ってこられない、このデータからしか生まれない絵になる。

## 2. 全体の位置づけ

利用者の要望は3つのフェーズに分かれる。本書は2Aのみを扱う。

| | 内容 | 着手条件 |
|---|---|---|
| **フェーズ2A（本書）** | 施設名検索、B2デザイン刷新 | 今すぐ |
| フェーズ2B | 情報の自動収集と再構成（事実抽出・裏付け・矛盾の記録） | 2A完了後 |
| フェーズ3 | HotPepper / Yahoo 統合、SEO、PWA | 利用者のAPIキー登録後 |

2Bを分けるのは、検索API経由の事実抽出と信頼度計算がそれ自体で独立した subsystem であり、デザイン刷新と同時にやると障害が絡み合って原因が追えなくなるためである。

## 3. 決定事項

| 論点 | 決定 |
|---|---|
| デザイン方向 | **B2「一軒入魂」** — 全画面1軒、縦スワイプで次へ |

## 4. 画面構成

### 4.1 「探す」タブ＝縦スワイプデッキ

1画面に1軒。上スワイプ（またはキーボードの ↓ / PageDown）で次の施設へ。

並べ替えがそのままデッキの順序になる。「発見が多い順」にすれば穴場と孤立店が次々に流れてくる。これが**この形を選んだ理由**である。一覧では埋もれる発見が、全画面なら1軒ずつ立つ。

**1枚のカードに載るもの:**

- 背景 — その施設を中心とした**星座図**（§5）
- アイブロウ — `地名 / カテゴリ`（例 `BEPPU / 映画`）
- 施設名 — 最大級の見出し。明朝
- **データから生成した一文**（§6）
- 徒歩◯分 — 見出しと同格の大きさ。ゴシック。その下に直線距離と方角
- 3軸のチップ、営業状態、チェーン／穴場／孤立のバッジ
- 星（保存）

**カードをタップまたは上に引くと、既存の詳細シートが開く。** 地理院タイル地図、営業時間、電話、サイト、経路リンクはそこにある。作り直さない。

### 4.2 絞り込みとヘッダー

全画面の絵をUIで埋めては意味がない。絞り込みは常時表示をやめ、上部の1ボタンからシートで開く。

ヘッダーに残すのは最小限とする。検索起点のラベル（`別府駅 から近い順`）、絞り込みボタン、並べ替えボタン、そして「一覧で見る」。

### 4.3 一覧表示を残す理由

全画面デッキだけにすると、**見渡すという行為ができなくなる**。「この辺に何があるか把握したい」は実在する使い方であり、37,193件を持つ強みもそこで出る。既存の一覧はそのまま残し、切り替えで行き来する。

デッキと一覧は**同じ絞り込み・同じ並べ替え・同じ結果集合**を共有する。片方で絞ってもう片方に移ったとき結果が変わってはならない。

### 4.4 現在の画面との関係

現行の3タブ構成（探す / 全国で見る）は維持する。「探す」の中身がデッキになるだけである。「全国で見る」（県別ヒートマップ）には手を入れない。

## 5. 星座図

### 定義

その施設を中心とした半径1.5km以内の全施設を、実座標のまま点で打った図。色はカテゴリ別。中心の施設だけを金色の輪で囲む。

同心円を3本（500m / 1km / 1.5km）薄く敷き、距離感を出す。

### 計算

読み込み済みの `PREF_CACHE` から算出する。追加の取得は行わない。

投影は中心施設まわりの局所正距円筒とする。

```
x = (lon - lon0) * cos(lat0) * 111320
y = -(lat - lat0) * 111320
```

半径1.5km を SVG の半径 R へ線形写像する。

### 性能

東京都は1県で5,968件ある。カードごとに全件走査すると、高速スワイプで詰まる。**施設IDをキーにした計算結果のキャッシュを持ち、1施設につき1回だけ計算する。** 上限は直近200件とし、それを超えたら古いものから捨てる。

点が多すぎる場合は**中心に近い順に120点まで**に制限する。都心では1.5km圏に数百件あり、全部打つと黒い塊になって何も読み取れない。

### なぜこれが価値なのか

「密集」と「孤立」を同じ絵で語れる。別府駅前は温泉が密集し、山間の一軒は点が疎になる。**どちらも1枚の絵で伝わる。** そして他社は同じ絵を作れない。この分布はこのデータセット固有のものである。

## 6. 生成する一文

### 方針

**手書きしない。** 37,193件すべてに付けるには、データから決定的に生成する純関数でなければならない。

`leadSentence(item, ctx) -> string` を `assets/hitori/core.js` に置き、Node でテストする。

### 構造

**1文目は必ず数字を伴う具体的な事実、2文目は軸の節をひとつだけ。**

当初は候補を上から2つ採る設計にしたが、実データ3県8,166件で検証したところ、静けさ5・入りやすさ5の業態（ネットカフェ・映画館・図書館）がすべて「会話が発生しない。作法は要らない。」になり、**全体の17%が同じ文**になった。1文目に施設ごとに異なる数字を必ず入れる構造へ変更した結果、異なる文が519→2,736種類、最頻の文が17%→1.56%になった。

**1文目（上から最初に当たったもの1つ）:**

| 条件 | 生成する節 |
|---|---|
| 孤立バッジが立つ | `最寄りの{カテゴリ}まで{距離}。この一帯で唯一。` |
| 穴場バッジが立つ | `周辺{hidden_n}軒中{chain数}軒がチェーン。その中の一軒。` |
| 半径500m内の同業態が3件以上 | `半径500mに同じ{業態}が{n}軒。` |
| 上記いずれも該当しない | `最寄りの{カテゴリ}まで{距離}。` |
| 孤立度すら渡されていない | `{業態}。ひとり度{solo}。` |

**2文目（上から最初に当たったもの1つ。無ければ1文で終える）:**

| 条件 | 生成する節 |
|---|---|
| `quiet >= 5` | `会話が発生しない。` |
| `quiet <= 2` | `声を出す場。` |
| `easy <= 2` | `常連の作法がある。` |
| `easy >= 5` | `作法は要らない。` |
| `solo == 5` | `ひとりが標準。` |

### 孤立度はカテゴリ単位である

`iso` は同じ**カテゴリ**（湯・サウナ／カウンター飲食／ひとり娯楽／ひとり滞在）までの距離であり、同じ業態までの距離ではない（`scripts/hitori/iso.py` の `_nearest_same_cat`）。したがって孤立を語る節では業態名を使ってはならない。「最寄りのネットカフェまで4.6km」は事実でない文になる。

公開済みの詳細シートが同じ誤りをしていたため、本フェーズで併せて修正した。

### 禁止事項

生成文で**断定してはならないこと**がある。営業時間が不明な施設に「今なら空いている」とは書かない。3軸は業態からの推定であり、「静かです」と言い切らず「会話が発生しない」という業態の性質として書く。この区別は既存の免責文と整合する。

## 7. 施設名検索

### 二段構え

**第一段** — 読み込み済みの県（自県＋隣接、通常4〜5県）の施設名を部分一致で検索する。追加ダウンロードはゼロ。即座に返る。大半の検索はここで済む。

**第二段** — 第一段で0件だったとき、または利用者が明示的に押したときに限り、`data/hitori/facilities.json` を取得して全国を検索する。ボタンには**取得量を明記する**（`全国から探す（初回のみ約380KB）`）。黙って落とさない。

### 検索欄の統合

検索欄は1つのまま、駅・地名と施設を横断して探す。結果は見出しで分ける。

```
駅・地名
  別府駅（大分県）
  別府市（大分県）
施設
  駅前高等温泉（大分県・温泉）
  別府ブルーバード劇場（大分県・映画館）
```

**駅・地名を上に置く。** 「どこを起点にするか」のほうが「特定の店を開く」より頻度が高い。

施設を選んだときは、**起点を変えずにその施設のカードを直接開く**。駅を選んだときは起点が変わる。この違いを結果の見出しで示す。

### 全国インデックス

`data/hitori/facilities.json`（新規、ビルド生成物）。

```json
{
  "updated": "2026-08-08",
  "fields": ["name", "pref", "i"],
  "items": [["駅前高等温泉", 44, 12], ["別府ブルーバード劇場", 44, 37]]
}
```

`i` は **その県ファイル `items` 配列の添字**である。施設IDを持つより軽い（実測 gzip 534KB → 378KB）。選択後にその県のファイルを取得すれば残りの情報は揃うため、この索引は**探すためだけのもの**でよい。

**整合の担保。** 添字は生成時点の県ファイルに対応する。両者は同じビルドが生成するので通常はずれないが、片方だけ古いと**別の施設を開くという静かな誤り**になる。`updated` を両方に持たせ、ランタイムで突き合わせる。不一致なら全国検索を無効化し、「データの更新中です」と出す。誤った施設を開くよりよい。

## 8. データスキーマの変更

`pref/{code}.json` と `summary.json` と `places.json` は変更しない。

`facilities.json` を新規に追加する（§7）。

## 9. 失敗の扱い

| 状況 | 挙動 |
|---|---|
| `facilities.json` の取得に失敗 | 「全国データを読み込めませんでした」と再試行ボタン。第一段の検索は生かす |
| `facilities.json` と県ファイルの `updated` 不一致 | 全国検索を無効化し理由を出す。**誤った施設を開かない** |
| 添字が県ファイルの範囲外 | その候補を出さない。コンソールに警告 |
| 星座図の周辺施設が0件 | 中心点と同心円だけを描く。空白にしない |
| 生成文がどの条件にも当たらない | 業態とひとり度の素っ気ない事実を返す。空文字を返さない |
| デッキが0件 | 「この条件に該当する施設はありません」と絞り込みを開くボタン |
