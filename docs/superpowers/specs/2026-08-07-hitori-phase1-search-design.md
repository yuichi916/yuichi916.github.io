## 1. なぜこれをやるのか

公開版は現在地からしか探せない。明日の出張先も、週末に行く街も調べられない。**「今ここ」以外を調べられないことが、このアプリを実用にしていない最大の理由**である。

同時に、発見機能が飲食と娯楽に偏っている。穴場スコア（周囲のチェーン比率）は湯1.4%・滞在0.2%というチェーン率の低さゆえに、この2カテゴリでは構造的に0件になる。銭湯とサウナを探しに来た人に、何の発見も返せていない。

フェーズ1はこの2つを埋める。

## 2. 全体の位置づけ

利用者の要望「多角的なデータ、UI/UXの工夫、商用レベルの完成度」は3つのフェーズに分解した。本書はフェーズ1のみを扱う。

| | 内容 | 着手条件 |
|---|---|---|
| **フェーズ1（本書）** | 駅名・地名検索、孤立度、並べ替え、お気に入り | 今すぐ |
| フェーズ2 | HotPepper / Yahoo の統合と名寄せ | 利用者のAPIキー登録後 |
| フェーズ3 | オンボーディング、速度、SEO、PWA、共有 | 中身が揃ってから |

フェーズ3を先にやらない理由は、薄い情報を綺麗に見せても実用性は上がらないからである。

## 3. 決定事項

| 論点 | 決定 |
|---|---|
| 営利性 | **非営利のまま**。広告・課金・アフィリエイトを置かない |
| 口コミ | **公式情報のみ**。Google Places の有料利用はしない |
| 地名検索の方式 | **自前インデックスを同梱**。外部ジオコーディングAPIに依存しない |
| 孤立度の定義 | 最寄の同業態施設までの距離 |
| 孤立バッジのしきい値 | **実測した分布から、カテゴリ別に決める**（§6） |
| 並べ替え | 距離順（既定）＋ ひとり度 / 発見度 / 静けさ / 営業中優先 |
| お気に入り | localStorage。アカウントもサーバーも持たない |

### 地理院の地名検索APIを使わない理由

`https://msearch.gsi.go.jp/address-search/AddressSearch` を実測した（2026-08-07）。`渋谷駅` でも `東京都渋谷区道玄坂` でも空配列 `[]` が返る。住所検索専用のうえ現状動作しておらず、依存先にできない。

自前インデックスなら外部依存がなく、ネットワーク往復もなく、日本の利用者が実際に打つ語（駅名）に直接当たる。

## 4. 検索インデックス

### 中身

| 種別 | 出典 | 件数 |
|---|---|---|
| 鉄道駅 | OSM `railway=station` かつ `name` あり | **9,128**（実測 2026-08-07） |
| 市区町村 | OSM `admin_level=7` の境界 relation | 1,700〜1,950 を想定（日本の市区町村は約1,741） |

合計およそ 11,000 件。

### ファイル

`data/hitori/places.json`。列指向で持つ。

```json
{
  "updated": "2026-08-07",
  "fields": ["name", "lat", "lon", "type", "pref"],
  "items": [
    ["渋谷駅", 35.65806, 139.70166, "s", 13],
    ["渋谷区", 35.66380, 139.69800, "c", 13]
  ]
}
```

`type` は `s`（駅）/ `c`（市区町村）。座標は小数5桁。**目標は生300KB以下・gzip 100KB以下**、テストで上限を検証する。

### 読み込みのタイミング

**初期ロードには含めない。** 利用者が検索欄にフォーカスした時点で初めて取得する。現在地から使う人に無駄な100KBを負わせないため。取得中は検索欄に「読み込み中」を出す。

### 照合

クライアント側の部分一致。正規化は最小限にする。

- 入力と候補名の両方について、前後の空白を除去する
- ひらがな・カタカナの相互変換はしない（OSMの `name` は漢字が主で、かな入力での一致は期待できない。かな対応は `name:ja-Hira` の被覆率を測ってから別途判断する）
- 「駅」の有無を両方向で吸収する。単純な部分一致だけでは、入力 `渋谷駅` に対して OSM 側の名前が `渋谷` の駅を取りこぼす。**入力そのものと、入力の末尾から `駅` を除いたものの両方で照合し、和を取る**
- 上位20件まで表示。駅を市区町村より上に出す（利用者が打つのは駅名のほうが多い）

**同名駅の扱い。** 日本には同名の駅が複数ある（府中駅、大久保駅など）。候補の表示は必ず `駅名（都道府県名）` の形にし、どれを選んだかが分かるようにする。

## 5. 検索起点の切り替え

現在地と、選んだ地点は**同格の「検索起点」**として扱う。

```
state.origin = { kind: 'here' | 'place', lat, lon, label }
```

- 起動時は `kind: 'here'`、`label: '現在地'`
- 地点を選ぶと `kind: 'place'`、`label: '渋谷駅'`
- 一覧の上に常に「**渋谷駅** から近い順」と出し、その隣に「現在地に戻す」を置く

現在地が取れていない状態でも地点検索は使える。これが本フェーズの核心であり、位置情報を拒否した人でもアプリが機能するようになる。

**県データの読み込みは起点に従う。** 起点の座標から `core.prefectureAt` で県を判定し、その県と隣接県を読む。現在地のときと同じ経路を通す。

## 6. 孤立度

### 定義

`iso_m` = その施設から**最寄の同カテゴリ施設までの距離**（メートル、整数）。

「最寄りの銭湯まで4.2km — この一帯で唯一」と説明できることが、この指標を選んだ理由である。

### 計算

穴場と同じくビルド時に全国の点集合に対して行う。県別にやると県境で最寄が誤る。既存の `scripts/hitori/hidden.py` のグリッド走査を流用するが、**探索半径が大きく異なる**点に注意する。穴場は500m固定だが、孤立度は最寄が見つかるまで広げる必要がある。

グリッドセルを 0.01度（約1.1km）とし、中心セルから同心リング状に外側へ広げて同カテゴリ施設を探す。

**リング r で候補が見つかっても、そこで打ち切ってはならない。** グリッドは正方形なので、リング r の隅にある候補より、リング r+1 の辺の中央にある候補のほうが近いことがある。候補が見つかったら、その距離を `d` として **`d` を含みうる最外リングまで走査してから**最小値を確定する。具体的には、リング r で `d` を得たら `ceil(d / セル幅)` リングまで探索を続ける。

上限は 50km とし、それを超える場合は `iso_m = 50000` で打ち切る（離島など）。

同カテゴリが全国で自分1件だけの場合も `50000` とする。

### バッジのしきい値

**固定値を置かない。** 穴場で全カテゴリ共通の0.6を置いて湯・滞在が構造的に0件になった失敗を繰り返さないため、ビルド時にカテゴリごとの `iso_m` 分布を出し、**そのカテゴリの90パーセンタイル**を孤立バッジの境界とする。

閾値は `summary.json` に書き出し、画面はそれを読む。Python と JS に同じ数字を二重に持たない。

```json
"iso_threshold": { "bath": 3200, "eat": 900, "play": 5400, "stay": 2100 }
```

上の値は書式の例であり、実測値ではない。ビルドが算出する。

ビルド後に各カテゴリの実測分布（中央値・90パーセンタイル・最大）を報告し、`bath` で妥当な件数のバッジが付くことを確認する。**湯で0件になるなら設計が失敗している**ので、その場合は分位を下げるのではなく原因を調べる。

### 表示

```
孤立度  最寄りの銭湯まで 4.2km（この一帯で唯一）
```

閾値未満の施設にはバッジを出さない。`iso_m` 自体は詳細シートに常に出す（距離が近いこと自体は有用な情報である）。

## 7. 並べ替え

既定は距離順。加えて4つ。

| 値 | 表示名 | 並べ方 |
|---|---|---|
| `dist` | 近い順（既定） | `distM` 昇順 |
| `solo` | ひとり度が高い順 | `solo` 降順 → `distM` 昇順 |
| `find` | 発見が多い順 | 発見スコア降順 → `distM` 昇順 |
| `quiet` | 静かな順 | `quiet` 降順 → `distM` 昇順 |
| `open` | 営業中を優先 | 営業状態 → `distM` 昇順 |

**発見スコア**は穴場度と孤立度を統合した0〜1の値とする。カテゴリによって効く指標が違うため、両方を正規化して大きいほうを採る。

```
find = max(hidden, min(1, iso_m / iso_threshold[cat]))
```

飲食・娯楽では `hidden` が効き、湯・滞在では `iso_m` が効く。どちらのカテゴリでも「発見が多い順」が意味を持つ。

**営業中優先の並び順は 営業中 → 不明 → 営業時間外 とする。** 不明を営業時間外より下に置いてはならない。不明な店は開いている可能性があり、閉まっていると確定した店より見込みがある。この順序は「分からないものを分からないと言う」という既存の原則の並べ替え版である。

## 8. お気に入りと履歴

サーバーもアカウントも持たない。localStorage のみ。

### 保存するもの

```
hitori.favs    施設のスナップショット配列（最大200件）
hitori.recent  最近見た施設のID配列（最大30件）
hitori.places  最近使った検索起点（最大10件）
```

お気に入りは**IDだけでなくスナップショットを保存する**。IDだけだと表示に県ファイルの取得が要り、複数県にまたがるお気に入りを開くたびに数MBを読むことになる。保存するのは `id, name, lat, lon, cat, kind, solo, quiet, easy, chain, prefCode` の11項目で、1件あたり約120バイト、200件で24KB。

スナップショットは**保存時点のデータ**である。再ビルドで施設が消えたり評価が変わっても、お気に入りは古い値を表示し続ける。詳細シートを開いたときに現行データと突き合わせ、施設が見つからなければ「この施設は現在のデータに存在しません」と出す。黙って古い情報を見せない。

### 画面

「探す」タブの上部に、お気に入り件数のチップを置く。押すと一覧がお気に入りに切り替わる。お気に入り表示中は起点からの距離も出す（保存した店が今どのくらい近いかは有用である）。

各行と詳細シートに星ボタンを置く。押した瞬間に保存し、確認は求めない。

### localStorage が使えない場合

プライベートブラウジングなどで `localStorage` が例外を投げる環境がある。**書き込みを try/catch で囲み、失敗したらお気に入り機能を静かに無効化する**（星ボタンを隠す）。アプリ全体を落としてはならない。

## 10. 失敗の扱い

| 状況 | 挙動 |
|---|---|
| `places.json` の取得に失敗 | 検索欄に「地名データを読み込めませんでした」と再試行ボタン。現在地からの探索は生かす |
| 検索語に一致なし | 「該当する駅・地名がありません」。入力の一部で再検索を促す |
| 選んだ地点の県データ取得に失敗 | 既存と同じく県名を挙げて報告する |
| `localStorage` が例外を投げる | お気に入り機能を無効化。アプリは動かす |
| お気に入りの施設が現行データに無い | 詳細シートで「現在のデータに存在しません」と明示 |
| `iso_m` が上限50000 | 「最寄りが50km以上」と表示。数値を偽らない |
