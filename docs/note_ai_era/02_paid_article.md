# AIエージェントに任せると「完成しているのに違う」ものが返ってくる人へ。原因はプロンプトではなく、“止まる場所”が消えたことでした

161本の音声が、数週間、無音のまま公開されていました。

エラーは一度も出ていません。画面は普通に進み、字幕も正しく出ていました。声だけがありませんでした。エージェントは作業のたびに「完了しました」と報告していて、私はそれを信じていました。

AIエージェントに任せると、ときどきこういうものが返ってきます。

動く。整っている。報告も丁寧。でも、違う。

そして、違うと気づくのは、たいてい公開したあとです。

この記事は、AIエージェント（主に Claude Code）と16作品を作って公開するあいだに、同じ形の失敗を何度も踏んだ記録です。それを止めるために置き直した「止まる場所」の話でもあります。

先に書いておきます。稼ぐ話は出てきません。「AIで月◯万円」は一行もありません。出てくるのは、公開前に止められたもの、捨てずに済んだものの話です。

---

## こんな経験はありませんか

当てはまるものを数えてみてください。

- [ ] エージェントの「完了しました」を、自分で動かす前に信じたことがある
- [ ] できあがったものを見て「なんか違う」と思ったのに、どこが違うのか言えなかった
- [ ] 1時間で出てきたものを、方向が違うと分かっていても捨てられなかった
- [ ] 手元では動いていたのに、公開されていたのは古い版だった
- [ ] 専門外の出力（デザイン、音、英語、コード）を「よさそう」で通した

2つ以上当てはまるなら、原因はたぶんプロンプトの書き方ではありません。

---

## なぜそうなるのか ― 実装の遅さが、検問所だった

人が手で作っていた頃、曖昧な指示はそれほど怖くありませんでした。

書き始めれば、手が止まるからです。「ここ、どうするんだっけ」で作業が物理的に止まり、そこで考え直す機会が来ました。3日かかると分かっている仕事なら、始める前に何度か考え直します。

**実装が遅いあいだは、その遅さが品質保証の一部でした。**

AIエージェントは、曖昧な指示の前でも止まりません。行間を埋めて、それらしいものを完成まで持っていきます。速さは本物です。ただ同時に、考え直す機会だった「詰まり」が消えました。

| | 人が作っていた頃 | エージェントに任せる今 |
|---|---|---|
| 曖昧な指示を受けると | 手が止まる | 止まらない |
| 失敗の形 | 未完成 | 完成しているが違う |
| 気づく時期 | 作業中 | できあがってから（多くは公開後） |
| 捨てるコスト | 時間 | 時間 ＋「もったいない」 |

止まらない相棒と組むなら、止まる場所は人間の側で置き直すしかありません。

## このまま続けると、何が起きるか

私が実際に踏んだものを並べます。

**気づくのが、いつも公開のあとになります。**
- 冒頭の161本の無音は、改稿で本文を1文字直すたびに音声の参照先が変わる仕組みが原因でした。エラーは出ないので、数週間、誰も気づきませんでした。
- 多言語版では、翻訳ファイルのデプロイを忘れたときに「翻訳が無ければ原文を出す」という安全な仕組みが働き、**全言語が完璧な日本語で表示されました**。ローカルのテストは全部通っていました。手元には正しいファイルがあったからです。

**捨てられなくなります。**
1時間で完成品が出てくると、方向が違っていても捨てにくくなります。速さは、判断を歪める方向にも働きます。

**自分の感覚は、当てになりません。**
METR の実験では、経験のある開発者が「AIのおかげで20%速くなった」と感じていたのに、実測では19%遅くなっていました（2025年）。Stack Overflow の2025年調査では、AIへの不満の1位が「ほぼ正しいが、正しくない」でした。

**専門外では、平均が出荷されます。**
良し悪しを判定できないまま「よさそう」で通すと、整っているのに誰の記憶にも残らないものができます。

**そして、学べません。**
私は「採点もエージェントにやらせればいい」と考えて、試しました。回りませんでした。採点は返ってきますが、その採点が甘いのか辛いのかを、私が判定できなかったからです。

## 読み終わると、何が変わるか

| | Before | After |
|---|---|---|
| 頼み方 | 「いい感じに作って」 | 最初に規模と「私が決めること」を出させる |
| 完了 | 「できました」を信じる | 完了を、コマンドの出力で受け取る |
| 確認 | 手元で開いて目で見る | 公開されている実物を機械で照合する |
| 専門外 | 「よさそう」で通す | 2〜3案を並べて選び、選んだ理由を1行残す |
| 失敗に気づく人 | 公開後の読者 | 公開前の自分とスクリプト |

私の場合、専門外6分野で13日間に打った指示80件を読み直すと、出てきたものへの指摘のうち**原因を名指しできたものが、前半の14%から後半の73%に増えていました**（分類は私の手作業です。詳細と限界は有料部分に書きます）。

この仕組みを通して公開した作品では、日英あわせて474本の音声を検査し、欠落0、孤児0でした。

## 解決の地図 ― 止まる場所を3つ置く

やることは単純です。エージェントの前に1か所、後ろに2か所、止まる場所を置きます。

```
 ┌──────────┐     ┌────┐     ┌──────────────┐     ┌──────────────┐     ┌──────────────┐
 │門1 決めさせる│ → │ 作る │ → │門2 数えさせる │ → │ 門3 選ぶ      │ → │公開物で確かめる│
 │（作る前）   │     └────┘     │（真偽・機械）  │     │（良否・人間）  │     └──────────────┘
 └──────────┘                  └──────────────┘     └──────────────┘
  整合しているが違う      静かに壊れる          判定できないまま出荷
  を止める               を止める              を止める
```

- **門1 決めさせる（作る前）**
  エージェントに作らせる前に、私が決めるべきことを出させて、決めます。止めるのは「整合しているが、作りたかったものではない」失敗です。
- **門2 数えさせる（作った後／真偽）**
  指定したものを使ったか。参照先は実在するか。数字は出典と合っているか。これは知識がなくても機械で守れます。止めるのは「エラーを出さずに壊れる」失敗です。
- **門3 選ぶ（作った後／良否）**
  狙ったものになっているか。これは人間にしか決められません。ただし「判定する」のではなく「並べて選ぶ」形にすると、専門外でもできます。

16作品を作ってたどり着いた結論は、1つです。

**AIに任せられないのは実装ではありません。何を作るかを決めることと、できたものが違うと認めること。この2つだけです。**

3つの門は、この2つを人間の手元に残すための仕組みです。

## 今日から使える1文

無料部分の最後に、いちばん効いた1文を置いておきます。何かを頼むとき、最初にこれを打ってください。

```
この作業で私が決めないといけないことを、重要な順に5つ挙げて。
それぞれ選択肢と、選択が結果に与える違いも書いて。
```

何を決めるべきかを知らないうちは、良い指示は書けません。だから質問ごと出させます。返ってくる一覧が、そのままその分野の評価軸のリストになります。

たとえば3Dの背景でこれをやると、「視点の高さ」「霧の量」「光源の色温度」「素材の密度」が並びます。私は最初、「背景が真っ黒」としか言えませんでした。この一覧を見ていたら、「暗い」以外の言葉が4つ、目の前にあったはずです。同じ背景を、2日半で6回作り直さずに済んだかもしれません。

もう1つ、エラーを出さない壊れ方の一覧も置いておきます。自分の作ったものに、どれか当てはまらないか見てみてください。

| 種類 | 起きること | 画面上の見え方 |
|---|---|---|
| 無音 | 音声ファイルが見つからない | 普通に進む。声だけ無い |
| 誤読 | 漢字を別の読みで発音する | 字幕は正しい。音だけ違う |
| 空のフォールバック | 翻訳が無く、原文に退避する | 完璧に表示される。ただし全部原文の言語 |
| 未デプロイ | 手元は正しく、公開物が古い | ローカルのテストは全部通る |

**向いている人**

## 1. 全体の順番（これだけ覚えれば回ります）

私が毎回やっている順番です。

1. **規模を宣言させる**（調べる／限定／構造）。迷ったら重い方にします
2. **決めることを5つ出させる**（無料部分の1文）
3. **質問は1問ずつ受けて、答える**
4. **案を2〜3個出させて、選ぶ**
5. **設計を見せてもらい、「これでいい」と言ってから着手させる**
6. **完了を、どうやって観測するかを先に決める**
7. 作らせる
8. **機械の検問を通す**（門2）
9. **別のエージェントに審査させる**
10. **人間が選ぶ・認める**（門3）
11. 公開する（公開の最終判断は人間の一言で）
12. **公開されている実物で確かめる**

太字が「止まる場所」です。多く見えますが、小さな依頼なら1〜6は2文で終わります。**省くのではなく、短くします。**

「単純すぎて確認は要らない」と思ったときが、いちばん危ないときです。単純な依頼ほど、前提が確かめられないまま進みます。多言語版で全言語が日本語になったのは、まさに「フォールバックを足すだけ」の小さな変更でした。

## 2. そのまま貼れる運用規約

リポジトリの直下に `CLAUDE.md`（Claude Code の場合）や `AGENTS.md`（Codex など）として置きます。コードを書かない作業なら、チャットの最初に貼ってください。

```markdown
# 作業規約（人間とエージェントの約束）

## 0. 規模を宣言してから始める
- 依頼を受けたら、最初の行で次のどれかを宣言する。
  - 調べる: 可否を確かめるだけ。作ったものは捨てる前提
  - 限定: 既存への小さな変更。短い設計を示してから着手する
  - 構造: 新規、または複数箇所に影響する。質問 → 案の比較 → 設計 → 計画の順で進める
- 迷ったら重い方を選ぶ。途中で複雑さが見つかったら、格上げして宣言し直す。格下げはしない。

## 1. 作る前に決めさせる
- 着手前に、私が決めるべきことを重要な順に最大5つ挙げる。それぞれに選択肢と、選択による結果の違いを書く。
- 質問は一度に1つだけ。
- 案は2〜3個。各案に「狙い」と「捨てたもの」を書く。
- 設計で「この設計が破綻する場面」を3つ挙げる。
- 設計を示し、私が「これでいい」と言うまで着手しない。設計が2文でも、この門は省かない。

## 2. 完了は観測で言う
- 着手前に、完了を確かめるコマンドと、期待する出力を書く。
- 「完了しました」は、そのコマンドの実際の出力を添えたときだけ使う。
- 出力を添えられないときは「未検証」と書く。

## 3. 範囲を守る
- 変更した行は、すべて依頼にたどれること。
- 頼まれていない改善は、実装せずに「提案」として最後に書く。
- 作業の最後に、変更したファイルと、それぞれの理由を一覧にする。

## 4. 妥協を隠さない
- 道具が動かないなどの理由で品質を落とした版を、完成品として出さない。
- 方針を変えたら、報告の最初の行で「方針を変えた」と言う。
- 取得や計測に失敗した値を、0や空で埋めない。null にして「取得できなかった」と書く。

## 5. 公開物で確かめる
- 検証は、手元の作業コピーではなく、公開URLや配布物に対して行う。
- 反映を待つときは、新しい版にしか無い文字列で判定する。
- 生成物は両方向で数える。「参照されているのに無い（欠落）」と「あるのに参照されていない（孤児）」。

## 6. 報告の形
- 報告は次の4つに分ける: やったこと ／ 観測結果（コマンドと出力）／ やっていないこと ／ 私が判断すべきこと。
- 専門外の分野では、使った素材・設定・用語の名前を必ず書く（私が語彙を覚えるため）。
- 公開・投稿・削除は、私の明示的な指示があるまで行わない。
```

### 各条はどの事故から生まれたか

規約は、理由が分かっていないと守られなくなります。各条の由来を並べておきます。

| 条 | 生まれた事故 |
|---|---|
| 0 規模の宣言 | すべての依頼に重い手続きを課すと、守られなくなる。軽い依頼の門を「省く」のではなく「短くする」ために、重さを先に決める |
| 1 決めることを5つ | 3Dの背景を、2日半で6回作り直した。私の語彙が「暗い」しかなかった |
| 1 質問は1つずつ | まとめて5問聞かれると、人は雑に答える。1問ずつだと、答えるうちに自分でも決まっていなかったことに気づく |
| 1 破綻する場面を3つ | フォールバックが未デプロイを隠した事故は、この問いを飛ばしたときに起きた |
| 2 完了は観測で | 161本の無音は、「完了しました」の報告のまま数週間過ぎた |
| 3 範囲を守る | エージェントは親切なので、頼んでいない改善を混ぜてくる。レビューの範囲が膨らみ、事故の温床になる |
| 4 妥協を隠さない | 道具が動かなかったとき、「動く範囲で作った版」が完成品のように出てきた。悪意ではなく、指示を満たそうとした結果だった |
| 4 失敗を0で埋めない | 取得に失敗した項目を0で埋めると、数字はそろって見えるのに判断材料が静かに壊れる。無音と同じ病気 |
| 5 公開物で確かめる | 手元のテストは全部緑なのに、公開物は古かった |
| 5 新版にしか無い文字列 | 反映を待つ判定に旧版にも含まれる語を使い、反映前に「反映済み」と判定していた |
| 6 用語を必ず書く | 専門外の語彙は、エージェントが毎回、素材と設定の名前を書いてきたことで覚えた（§5） |
| 6 公開は明示指示で | 速さを優先すると、人が最終の文面を見ないまま公開まで進みうる |

## 3. 依頼テンプレート5種

### T1. 着手の1文（すべての依頼の最初に）

```
[やりたいこと]をしたい。
まず規模（調べる／限定／構造）を宣言して、
私が決めないといけないことを重要な順に5つ、選択肢と結果の違いつきで挙げて。
質問は1つずつにして。
```

### T2. 案の比較

```
案を3つまで出して。各案に次を書いて:
- 狙い（何を優先したか）
- 捨てたもの
- この案が失敗するとしたら、どんな場面か
私が選ぶので、どれが良いかの推薦は最後に1行だけ。
```

推薦を最後に1行だけにするのは、先に推薦を読むと選ぶ前に引っぱられるからです。案は3つまでにします。5つ出させると選べなくなり、「おまかせで」に倒れます。

### T3. 完了の観測表

着手前に、この表を埋めてもらいます。

```
| 工程 | 完了の観測（コマンドと期待する出力） |
|---|---|
| 例: 音声 | inventory.py の出力が「欠落=0 孤児=0」 |
| 例: 公開 | live_check.py の出力が「判定: ALL OK」 |
| 例: 表示 | patrol.py の出力が「判定: ALL OK」 |
| | |
```

「できました」ではなく、この表の右の列が埋まった状態を完了と呼びます。

### T4. 別のエージェントに審査させる

作ったエージェントとは別のセッション（別のエージェント）に渡します。同じエージェントの自己申告は、指示に答えた部分しか報告しないからです。

```
あなたは審査担当です。次の成果物を、観点「[事実／読みやすさ／狙いとの一致]」だけで審査して。
- 良い点は書かない。直す点だけ書く
- 各指摘に重大度（高・中・低）と、根拠（どこの何がそうか）をつける
- 事実の指摘は、照合した出典の一文を添える
成果物: [貼る]
狙い: [門1で決めた5つを貼る]
```

運用のルールは1つです。**事実の観点で「中」以上が0件になるまで公開しない。点数が高くても止めない。**

私はこれで、数字の自動照合をすり抜けた誤りを見つけてもらいました。「出力が40%速い」という一文です。正しくは「30%以上」でした。40%という数字は別の文脈（費用）で出典に存在したので、「その数字が出典にあるか」だけを見る照合器は素通りしていました。**機械は値を見て、文を読む担当は別に要ります。**

### T5. 専門外の振り返り（門3のあと）

```
私が今選んだ案について、
「私がなぜそれを選んだと、あなたは理解したか」を1行で書いて。
その1行で、次の依頼文を書き直して。
```

この1行が、次の依頼文になります。借り物の言葉で構いません。私は同じ語を3回ほど使ったあたりで、調べ直さずに書けるようになりました。

## 4. 静かな不具合を拾う検問スクリプト3本

門2は機械に任せます。Python 3 で動きます。3本目だけ Playwright が必要です。

使い方は、エージェントに「このスクリプトを置いて、完了の観測に使って」と渡すだけです。

### S1. 参照と実ファイルを両方向で数える — `inventory.py`

```python
#!/usr/bin/env python3
"""参照と実ファイルを両方向で数える。欠落・孤児・破損疑いを出す。

使い方:
  # ソースの中に書かれたファイル名を拾う場合
  python inventory.py --src index.html js/*.js --assets assets/
  # ファイル名を計算で作っている場合（ハッシュ名など）は、期待リストを渡す
  python inventory.py --expected expected.txt --assets assets/voice/
"""
import argparse, pathlib, re, sys

p = argparse.ArgumentParser()
p.add_argument("--src", nargs="*", default=[], help="参照を探すファイル")
p.add_argument("--expected", help="期待するファイル名を1行1件で書いたテキスト")
p.add_argument("--assets", required=True, help="実ファイルのあるフォルダ")
p.add_argument("--ext", default="mp3,wav,ogg,png,jpg,jpeg,webp,svg,glb,json")
p.add_argument("--min-bytes", type=int, default=800, help="これ未満は破損疑い")
a = p.parse_args()

exts = [e.strip().lower() for e in a.ext.split(",")]
pat = re.compile(r"[\w\-./]+\.(?:%s)\b" % "|".join(map(re.escape, exts)), re.I)

refs = set()
for f in a.src:
    text = pathlib.Path(f).read_text(encoding="utf-8", errors="ignore")
    refs |= {pathlib.PurePosixPath(m).name for m in pat.findall(text)}
if a.expected:
    lines = pathlib.Path(a.expected).read_text(encoding="utf-8").splitlines()
    refs |= {pathlib.PurePosixPath(l.strip()).name for l in lines if l.strip()}

files = {f.name: f for f in pathlib.Path(a.assets).rglob("*")
         if f.is_file() and f.suffix[1:].lower() in exts}

missing = sorted(refs - files.keys())
orphan = sorted(files.keys() - refs)
tiny = sorted(n for n in refs & files.keys() if files[n].stat().st_size < a.min_bytes)

print(f"参照={len(refs)}  実ファイル={len(files)}  欠落={len(missing)}  "
      f"孤児={len(orphan)}  破損疑い(<{a.min_bytes}B)={len(tiny)}")
for label, items in (("欠落", missing), ("孤児", orphan), ("破損疑い", tiny)):
    for n in items[:50]:
        print(f"  {label}: {n}")
    if len(items) > 50:
        print(f"  {label}: ほか {len(items) - 50} 件")

sys.exit(1 if missing or tiny else 0)
```

出力はこうなります。

```
参照=3  実ファイル=3  欠落=1  孤児=1  破損疑い(<800B)=1
  欠落: gone.png
  孤児: orphan.png
  破損疑い: b.png
```

読み方は2つだけです。
- **欠落**があれば、そこは無音や画像切れになっています
- **孤児**があれば、何かを変えたのに気づいていません。こちらのほうが価値のある信号です

注意が1つあります。ファイル名を計算で作っている場合（台詞のハッシュを名前にしているなど）、ソースを文字で探しても参照は見つかりません。その場合は、同じ計算で「期待するファイル名の一覧」を書き出させて、`--expected` に渡してください。私の161本はまさにこの形でした。

### S2. 公開物と手元をハッシュで照合する — `live_check.py`

```python
#!/usr/bin/env python3
"""手元のファイルと、公開されている実物が同じかをハッシュで比べる。

使い方:
  python live_check.py --base https://example.com/ index.html assets/voice/k123.mp3
"""
import argparse, hashlib, pathlib, sys, time, urllib.request

p = argparse.ArgumentParser()
p.add_argument("--base", required=True, help="公開URLの起点（末尾は / ）")
p.add_argument("files", nargs="+", help="手元のパス（公開URLでも同じ相対パスのもの）")
a = p.parse_args()

bad = 0
for f in a.files:
    local = hashlib.md5(pathlib.Path(f).read_bytes()).hexdigest()
    url = a.base.rstrip("/") + "/" + f.lstrip("./") + f"?nocache={int(time.time())}"
    try:
        with urllib.request.urlopen(url, timeout=20) as r:
            remote = hashlib.md5(r.read()).hexdigest()
    except Exception as e:
        remote = None  # 取れなかったものを「一致」や空で埋めない
        reason = type(e).__name__
    if remote is None:
        status = f"取得できなかった ({reason})"
    elif remote == local:
        status = "一致"
    else:
        status = "不一致（公開物が古い／別物）"
    bad += status != "一致"
    print(f"{status:<24} {f}")

print(f"判定: {'ALL OK' if bad == 0 else f'{bad} 件を確認して'}")
sys.exit(1 if bad else 0)
```

```
一致                       index.html
不一致（公開物が古い／別物）           assets/lang/en.json
取得できなかった (HTTPError)     assets/lang/ko.json
判定: 2 件を確認して
```

全言語が日本語で表示された事故は、このスクリプトなら3行目で止まっていました。**手元の作業コピーは、いちばん信用できない場所です。**

### S3. 公開ページを巡回する — `patrol.py`

```python
#!/usr/bin/env python3
"""公開ページを巡回して、JSエラー・横はみ出し・内部リンク切れを数える。

準備: pip install playwright && playwright install chromium
使い方:
  python patrol.py --base https://example.com/ / /about.html /blog/
"""
import argparse, sys, urllib.error, urllib.parse, urllib.request
from playwright.sync_api import sync_playwright

p = argparse.ArgumentParser()
p.add_argument("--base", required=True)
p.add_argument("paths", nargs="+")
a = p.parse_args()
host = urllib.parse.urlparse(a.base).netloc

def page_status(url):
    try:
        with urllib.request.urlopen(url, timeout=20) as r:
            return r.status
    except urllib.error.HTTPError as e:
        return e.code
    except Exception:
        return None  # 取得できなかった。404とは区別する

bad, links = 0, set()
with sync_playwright() as pw:
    browser = pw.chromium.launch()
    for path in a.paths:
        url = urllib.parse.urljoin(a.base, path)
        row = []
        for label, width in (("PC", 1280), ("SP", 390)):
            pg = browser.new_page(viewport={"width": width, "height": 800})
            errors = []
            pg.on("pageerror", lambda e: errors.append(str(e)))
            pg.goto(url, wait_until="load")
            pg.wait_for_timeout(500)
            overflow = pg.evaluate(
                "document.documentElement.scrollWidth > window.innerWidth + 2")
            if label == "PC":
                row.append(f"err={len(errors)}")
                for href in pg.eval_on_selector_all("a[href]", "els => els.map(e => e.href)"):
                    u = urllib.parse.urlparse(href)
                    if u.netloc == host and u.scheme.startswith("http"):
                        links.add(href.split("#")[0])
            row.append(f"{label}溢={overflow}")
            bad += len(errors) + overflow
            pg.close()
        print(f"{path:<40} " + " ".join(row))
    browser.close()

broken = []
for link in sorted(links):
    st = page_status(link)
    if st != 200:
        broken.append((link, st))
print("内部リンク切れ: " + ("なし" if not broken else ""))
for link, st in broken:
    print(f"  {st if st is not None else '取得できなかった'}  {link}")
bad += len(broken)
print(f"判定: {'ALL OK' if bad == 0 else 'NG'}")
sys.exit(1 if bad else 0)
```

```
/                                        err=1 PC溢=True SP溢=True
/sub.html                                err=0 PC溢=False SP溢=False
内部リンク切れ:
  404  http://example.com/missing.html
判定: NG
```

横はみ出し（`SP溢=True`）は、スマホ表示の崩れでいちばんよく起きる形です。目で毎回確かめることはできないので、座標で判定させます。

### 回し方（中身より効きます）

- **毎回**: `patrol.py`（安いので、毎回回す）
- **素材を変えたときだけ**: `inventory.py`
- **公開のたび**: `live_check.py`

全部を毎回回すと、そのうち回さなくなります。**安いものは常に、高いものは条件付きで。**

もう1つ、検査が失敗を報告したときは、**検査のほうを疑う手順**も持っておきます。自動判定は間違えます。私は音声の自動書き起こしが異常な一致率を出したとき、音声の長さと音量の推移を見て「音声は正常、書き起こし側が壊れている」と切り分けました。

## 5. 専門外を任せるときの「目利き」― 3つの型

門3は人間の仕事です。ただ、専門外では「良いか悪いか」を判定できません。足場にできるのは1つだけでした。

**「AとBなら、Bのほうが自分の頭の中にあるものに近い」は、外の基準を必要としない。**

出来の良し悪しが分からなくても、これは言えます。ここから組み立てます。人間に残すのは「選ぶ」ことだけ。列挙と検算は、エージェントとスクリプトに出します。

### 型1. 決めるべきことを列挙させる

無料部分の1文です。自分で質問を考えるより速く、「何を知らなかったか」が先に見えます。

### 型2. 候補を並べて、差を見る

1つだけでは判定できません。でも、2つの差なら判定できます。

- 明るさを優先した版。建物は見えるが、床が空っぽ
- 密度を優先した版。暗いが、物が詰まっている

2枚を並べて初めて、私が欲しかったのは明るさではなかったと分かりました。**差分が、そのまま評価軸になります。**

### 型3. 真偽は、機械に検算させる

指定したものを使ったか。参照先は実在するか。仕様は合っているか。ここを目で見ている限り、良し悪しを見る余力は残りません。門2のスクリプトに出します。

### 効き目の記録（と、その限界）

3D、画像生成、音声合成、作曲、ゲームUI、物語の設計の6分野で、13日間に指示を80件打ちました。1日6件です。多くはありません。

80件のうち、新しく作らせる依頼と進行の催促を除いた40件が「出てきたものへの指摘」です。これを前半と後半に分けると、原因を名指しした指摘の割合は **14%から73%** に増えていました。

語彙は次の順に入れ替わりました。

1. 状態だけ（「背景が真っ黒」）
2. 部位（「床が」）
3. 理由（「物が無いから暗い」）
4. 原因の用語（「遠景に低ポリが混ざっている」）

ただし、正直に書いておきます。
- 分類は私の手作業で、境界は主観です。
- 前半の14%は、実数では2件です。
- 後半は指摘の数そのものが多く（前半14件、後半26件）、作業量の偏りで割合が変わって見えている可能性があります。
- 比較実験はしていません。言えるのは「割合が入れ替わった」までです。

効いた実感があるのは、次の2つです。
- 覚えた用語を、毎回1つ自分から使って指摘すること。使わなかった語は、ひとつも覚えていません。
- 完成させて公開すること。公開して初めて、自分の判定が当たっていたかが分かりました。

**専門外で最初に作るべきものは、成果物ではなく自分の判定力です。ただし判定力は、成果物を作らないと手に入りません。だから、作りながら育てるしかありません。**
