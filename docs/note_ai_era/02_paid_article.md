# Claude Codeの「確認疲れ」を減らす｜全部目で見なくても、ミスは公開前に止まる

Claude Code や Codex に任せたのに、確認で1日が終わっている人へ。その確認を「全部目で見る」から「仕組みで止める」に変える方法を書きます。

---

## 任せたのに、確認で夜が終わっていませんか

AIエージェントに仕事を任せるようになって、作業は確かに速くなりました。でも、楽になったかというと、そうでもない人が多いのではないでしょうか。

「完了しました」と言われても、そのまま出すのは怖い。だから全部開いて、目で確かめる。気づけば、作らせた時間より、確かめている時間のほうが長い。

かといって確かめるのをやめると、いつか何かが漏れる気がする。

全部見て疲れるか、見ないで怖いか。

私は一度、大きく漏らしています。

---

## 以前の私：161本の声が、数週間消えていた

AIエージェントと一緒に、ブラウザで遊べるサウンドノベルを作っていたときのことです。

161本の台詞が、数週間、無音のまま公開されていました。改稿で本文を直したときに、音声の参照先が変わっていたのが原因です。画面は普通に進み、字幕も正しく出ます。声だけがない。エラーは一度も出ていません。私を含めて、誰も気づきませんでした。

合成音声の読み間違いに初めて気づいたのも、読者からの一言でした。

「病だった、が、やまいだった、です」

テストは全部通っていました。

## 今の私：文面を読まずに「投稿して」と打つ

先日、深夜に Claude Opus 5.5 の発表を読んで、約1時間後には紹介動画をXに投稿していました。台本も、画面も、投稿文も、作ったのは Claude Code です。私が打った指示は2つだけでした。

「Opus5.5がリリースされたので、よくなったことを簡潔にまとめてXに投稿したい。紹介ビデオもあるといい」

「投稿して。youtube shortにも投稿して。１分AIにユースとして」

2つ目を打ったとき、私は最終の文面を読んでいません。

それでも、公開前に誤りが6件止まっていました。たとえば下書きには、こういう内容の一文がありました。

> 捏造が1つでもあれば不合格になるテストで、Fable 5.1 も Opus 5 も1本も通らなかった

数字は正しく、どちらの文も公式発表に実在します。ただ、発表には「なぜ落ちたか」が書かれていません。二文を並べただけで、「他のモデルは捏造した」と読める文になっていました。

見つけたのは、私ではありません。

変わったのは、目で見る量ではありませんでした。目で見るのを、やめたのです。なぜそれで止まるのか。先に、そもそもの原因を見ておきます。

---

## 「完了しました」が信じきれない、本当の理由

私は、AIエージェントが仕事ごとにどこまでできるかを、326の仕事について調べて地図にしています（[AIエージェント能力アトラス](https://yuichi916.github.io/ai-map.html)）。専門家と比べて0〜5の6段階で、すべてのマスに根拠のリンクを付けています。

その中に、並べると奇妙な2つがあります。

- テストコードを書く：**4（専門家並み）**
- 自分が書いたコードの正しさを確かめる：**2（補助）**

同じAIが、作るのは専門家並みなのに、自分の出来を確かめるのは補助どまり。根拠に挙げた調査には「過信により見落としを『問題なし』と報告する傾向が強い」とあります。

作る力と、確かめる力に、2段の差がある。「完了しました」は手を抜いた報告ではなく、確かめきれていない報告です。

その差を埋めるのが「最後に人間が確認」のはずでした。でも、エージェントの間違いは、たいてい「ほぼ正しい」形で出てきます。明らかにおかしいものは目で見つかりますが、ほぼ正しいものは目をすり抜けます。161本の無音も、さっきの一文も、そうでした。

全部を目で確かめ続ければ、自分がいちばん遅い工程になります。確かめるのをやめれば、読者が見つけます。どちらを選んでも、AIで速くなったはずの分が、どこかで帳消しになります。

## この記事を読むと、できるようになること

- 「完了しました」を、エージェントの報告ではなく、コマンドの出力で受け取れるようになる。コマンドを走らせるのはエージェントなので、自分で書けなくても大丈夫です
- 文章や数字の「ほぼ正しい」を、自分の目ではなく、別のエージェントに見つけさせられるようになる
- あなたが目を使うのは、最初に決めるときと、最後に選ぶときの2回だけになる

そのために、そのまま打てる依頼文4つ、確認を置き換えるスクリプト3本、CLAUDE.md にそのまま置ける作業規約をお渡しします。

## 人間は、最初と最後だけ

骨組みはこうです。

```
あなた   決める ─────────────────────────────── 選ぶ・違うと認める
機械           作る → 数える（抜け・食い違い・出典にない数字）
別のAI                 → 読む（数字のつなぎ方・抜けた条件・書いていない含意）
```

真ん中の確認は、人間がやりません。

あるはずのファイルがあるか。公開されたものが手元と同じか。本文の数字が出典にあるか。これは機械に数えさせます。数えられない「文の読み違い」は、作ったのとは別のエージェントに、事実の確認だけを任せて読ませます。Opus 5.5 の動画で6件を見つけたのは、この担当です。

人間がやるのは、最初に何を作るかを決めることと、最後にできたものを並べて選ぶこと。違っていたら、違うと認めて直すことです。

最後の仕事は、本当に最後まで残りました。あの動画の投稿文は、審査でいちばん点数が高かった案の切り口で書いたものでした。ところが1行目が細かい話から入っていて、公開してみると読まれていませんでした。「入口が細かすぎる」と1行目を書き直させたのは、私の一言です。

AIエージェントと16作品を作ってきて、人間から外せなかった仕事は、この二つだけでした。

---

## それでも、機械をすり抜ける誤りには型がある

ひとつ、正直に書いておきます。

本文の数字が出典にあるか、引用が原文にあるかは、機械で照合していました。あの6件は、その照合を全部通ったあとに見つかっています。数字も引用も正しいのに、文として間違っている。

分けてみると、型は3つしかありませんでした。

1. **条件の違う数字を、一つの文でつなぐ**
2. **内訳の一部だけを書いて、抜けた分を残りに押しつける**
3. **本物の二文を並べて、原文にない因果を作る**

「他のモデルは捏造した」と読めた一文は、3つ目です。

AIに資料や記事を書かせている人なら、どれかを見たことがあるはずです。気づかないまま出したことがあるかもしれません。

1. **全体の手順を1枚に**。着手前に書く3行から、公開後の確認まで
2. **そのまま打てる依頼文4つ**。決めさせる／比べさせる／完了を先に定義させる／別のエージェントに審査させる

## 1. 全体の手順

先に全体を1枚で置きます。細かいところは、このあとの章で一つずつ埋めます。

| 順 | やること | 誰が | 章 |
|---|---|---|---|
| 0 | 着手前に3行を書く（出力・入力・検証） | **あなた** | この章 |
| 1 | 「私が決めること」を出させて、決める | **あなた** | §2 依頼文1 |
| 2 | 案を2〜3個出させて、選ぶ | **あなた** | §2 依頼文2 |
| 3 | 完了を、どのコマンドの出力で確かめるかを先に決めさせる | エージェント | §2 依頼文3 |
| 4 | 作る | エージェント | — |
| 5 | 数える（抜け・食い違い・出典にない数字） | 機械 | §4 |
| 6 | 読む（数字のつなぎ方・抜けた条件・書いていない含意） | 別のエージェント | §2 依頼文4、§3 |
| 7 | 並べて選ぶ。違えば、違うと認めて直させる。「投稿して」 | **あなた** | — |
| 8 | 公開されたものを確かめる | 機械 | §4 |

あなたの出番は、0・1・2・7だけです。5・6・8のあいだ、目は使いません。

小さな依頼なら、0〜3は合わせて2〜3行で終わります。省くのではなく、短くします。「単純だから確認は要らない」と思ったときが、いちばん危ないときです。前提が確かめられないまま進むからです。

### 着手前の3行

エージェントに頼む前に、これを書きます。

```
出力: 何ができあがれば終わりか（文章／コード／図／公開済みのURL）を1行で
入力: AIに渡せる形で、手元にあるもの（テキスト・データ・URL・既存のコード）
検証: 結果が正しいと、どうやって分かるか
```

大事なのは3行目です。「テストが通る」「数字が出典と合う」「公開物が手元と一致する」のように、機械が答えを出せる形で書けるかどうか。

「自分が読んで、なんとなく」としか書けないなら、その仕事は任せる範囲を1段狭くします。能力の地図の使い方に書いた決まりと同じです。確かめる方法がない仕事は、段階を1つ下げて扱う。逆に3行目が書ければ、途中を見ずに任せられる範囲が1段広がります。

## 2. そのまま打てる依頼文4つ

### 依頼文1 ― 決めさせる

```
[やりたいこと]をしたい。
作り始める前に、私が決めないといけないことを、重要な順に5つ挙げて。
それぞれ選択肢と、選択が結果に与える違いも書いて。
質問は1つずつにして。
```

何を決めるべきかを知らないうちは、良い指示は書けません。だから質問ごと出させます。

私は3Dの背景を頼んだとき、「背景が真っ黒」としか言えず、同じ場所を2日半で6回作り直しました。背景についてこの依頼文を打つと、「視点の高さ」「霧の量」「光源の色温度」「素材の密度」が並びます。最初にこの4つが目の前にあれば、「暗い」以外の言葉で選べたはずです。

質問を1つずつにするのは、まとめて5問聞かれると、人は雑に答えるからです。1問ずつ答えていくと、自分でも決まっていなかったことに気づきます。

### 依頼文2 ― 比べさせる

```
案を3つまで出して。各案に次を書いて。
- 狙い（何を優先したか）
- 捨てたもの
- この案が失敗するとしたら、どんな場面か
どれが良いかの推薦は、最後に1行だけ。
```

1案だけでは、良いのか悪いのか判定できません。2案の差なら判定できます。差が、そのまま評価の軸になります。

案は3つまでにします。5つ出させると選べなくなり、「おまかせで」に倒れます。推薦を最後に1行だけにするのは、先に読むと、選ぶ前に引っぱられるからです。

### 依頼文3 ― 完了を先に定義させる

```
着手する前に、完了を確かめる方法を表にして。
| 工程 | 確かめるコマンド | 期待する出力 |
「完了しました」は、このコマンドの実際の出力を添えたときだけ使って。
出力を添えられないときは「未検証」と書いて。
```

エージェントの自己申告は、指示に答えた部分しか報告しません。3Dの背景を作り直したとき、エージェントが書いた作業の記録（コミットメッセージ）には「全方位を密なスラム建物で囲む閉塞感」とありました。やったことと合っています。床が一面のっぺりしていることは、書いてありませんでした。

完了の根拠を、報告の文章からコマンドの出力に移します。

### 依頼文4 ― 別のエージェントに審査させる

作ったのとは別のセッションで、事実の確認だけを頼みます。

```
あなたは事実の審査担当です。次の成果物を、事実の観点だけで審査して。
- 良い点は書かない。直す点だけ書く
- 各指摘に重大度（高・中・低）をつけ、原文の該当する一文をそのまま引用する
- 特に次の3つの型を探す
  A. 条件の違う数字を一つの文でつないでいないか（設定・期間・対象・母数が同じか）
     「なのに」「それでも」「さらに」「〜も」でつながった数字は必ず確かめる
  B. 内訳の一部だけを書いて、抜けた分を残りの項目に押しつけていないか
  C. 並べた二文のあいだに、原文に無い因果や含意が生まれていないか
- 最初の行に、審査したファイル名と更新日時を書く
成果物: [貼る、またはファイルのパス]
原文: [sources/ のパス]
```

最後の行は、審査の担当が、書き直す前の古いファイルを読んでいたことがあったので足しています。

### 審査の回し方

- **観点ごとに担当を分ける。** 1体に全部を見させると、平均的な答えしか返ってきません。Opus 5.5 の動画では、X用に「フック・形式」「意外性・戦略」「事実」の3体、YouTube用に2体を分けて、合計9回回しました。
- **事実の担当が落としたら、ほかが満点でも出さない。** 事実の「中」以上が0件になるまで直します。
- **直したら、もう一度回す。** 直したことで入る誤りがあります（次の章の⑤）。
- **1行目だけは、点数で決めない。** Opus 5.5 の動画の投稿文がそうでした。審査は、1行目でいちばん意外な細部を出す案に、いちばん高い点をつけました。でも読者は、まず何の話で、全体として何が変わったのかを知りたい。細部の意外さは、全体を言ったあとでないと効きません。

## 3. 動画の6件 ― 直す前と後

機械の照合（数字と引用）を通ったあとに、事実の審査担当が「中」と判定したものです。

| # | 直す前 | 直した後 | 型 |
|---|---|---|---|
| ① | Fable 5.1 並みの性能で、Opus 5 より約4割安い | **大半の作業で** Fable 5.1 並み。Opus 5 より約4割安く**動く** | C |
| ② | 見出し「Fable 5.1 並み」の下に、差がいちばん大きいベンチマークだけ | 2本立てにして、「実際に使うとスコアの差より小さい」の但し書き | B |
| ③ | 捏造が1つでもあれば不合格のレポート課題で、18本中16本合格 | 社内テストで、決算発表が見つけにくい条件。設定を変えて計18本 | C |
| ④ | Fable 5.1 も Opus 5 も1本も通らなかった | どれも通らなかった。**落ちた理由は書かれていない** | C |
| ⑤ | 単価 −20% ＋ 使うトークンも減る ＝ 約4割安い | 単価の値下げ ＋ トークンの減少 ＝ 約4割（キャッシュ読み取り −60% の行を戻す） | B |
| ⑥ | 費用が約4割減る。**それなのに**、評価は 52.3% から 66.4% に | 評価でも、**最高スコアは** 52.3% から 66.4% に | A |

### 型A ― 条件の違う数字をつなぐ（⑥）

「約4割」は既定の設定での試算、66.4% は最高の設定でのスコアでした。「それなのに」でつないだせいで、安い設定で高得点が出たように読めます。どちらの数字も正しいので、照合は通ります。

見分け方：二つの数字をつなぐ接続詞を探します。「なのに」「それでも」「さらに」「〜も」。見つけたら、両方の数字の条件（設定・期間・対象・母数）を原文で確かめます。

### 型B ― 内訳の一部だけを書く（⑤②）

⑤は、1回目の審査で「−20%と約4割の関係が分からない」と言われて式を足したときに入りました。画面を空けるためにキャッシュの行を外したので、残りを全部トークン削減の効果に見せてしまった。直したことで入った誤りです。

②も同じ形です。見出しは「並み」なのに、差がいちばん大きい棒だけを見せたので、大差に見えていました。

見分け方：合計や比較が出てきたら、内訳が全部書かれているかを確かめます。「＋α」「など」で省いた部分が、残りの項目に押しつけられていないか。

### 型C ― 書いていない含意を付ける（④③①）

本物の二文を並べただけで、原文にない因果が生まれます。④は無料部分で引いた一文です。①は「大半の作業で」という条件が落ちていました。

見分け方：原文の条件（「大半の」「ある社内テストで」「既定の設定で」）が、訳したあとに残っているかを見ます。直すときは、削るのではなく、「書かれていない」と書き足します。

## 4. 機械に数えさせる ― スクリプト3本

数えられるものは、全部機械に渡します。Python 3 で動きます。使い方は、エージェントに「このスクリプトを置いて、依頼文3の完了の確認に使って」と渡すだけです。

### 4-1. 数字と引用を照合する ― 根拠台帳と `check_ledger.py`

AIに数字の入った文章を書かせるなら、まず台帳を作らせます。

```
一次情報を保存して、本文だけのテキストにして sources/ に置いて。記憶にある情報は使わないで。
使う事実を ledger.json に1件ずつ登録して。各件に、原文の一文（quote）、使う数字（values）、
条件の読み方（reading）を書くこと。原文にその一文が無いものは登録しないで。
台帳に無い数字は、成果物に書かないで。
```

台帳の1件はこうなります。

```json
{
  "id": "L01",
  "ja": "大半の作業で Fable 5.1 並みの性能。Opus 5 より約4割安く動く",
  "values": ["40%", "4割"],
  "quote": "It performs at the level of Claude Fable 5.1 on most work and costs 40% less to run than Opus 5.",
  "source": "announce.txt",
  "reading": "on most work = 大半の作業で。全作業ではない。"
}
```

`reading` の欄が大事です。原文の条件をここで日本語にして固定しておくと、型Cの①のような「条件が落ちる」誤りが減ります。条件は、訳すときに落ちるからです。

照合するスクリプトです。

```python
#!/usr/bin/env python3
"""根拠台帳で、引用と数字を照合する。

1. 台帳の各 quote が、保存した原文にそのまま存在するか
2. 成果物に出てくる数字が、すべて台帳の values にあるか

使い方:
  python check_ledger.py --ledger ledger.json --sources sources/ --targets post.txt video.html
  （版数など、照合から外す数字は --ignore 5.5 4.0 のように渡す）
"""
import argparse, json, pathlib, re, sys, unicodedata

p = argparse.ArgumentParser()
p.add_argument("--ledger", required=True)
p.add_argument("--sources", required=True, help="原文を保存したフォルダ")
p.add_argument("--targets", nargs="+", required=True, help="照合する成果物")
p.add_argument("--ignore", nargs="*", default=[], help="照合から外す数字")
a = p.parse_args()

def norm(t):
    t = unicodedata.normalize("NFKC", t)
    t = re.sub(r"[“”„‟″]", '"', re.sub(r"[‘’‚‛′]", "'", t))
    return re.sub(r"\s+", " ", t)

NUM = re.compile(r"[$¥]?\d[\d,]*(?:\.\d+)?(?:%|割|倍|pt)?")
def nums(t):
    return {m.replace(",", "") for m in NUM.findall(norm(t))}

ledger = json.loads(pathlib.Path(a.ledger).read_text(encoding="utf-8"))
src = {f.name: norm(f.read_text(encoding="utf-8", errors="ignore"))
       for f in pathlib.Path(a.sources).iterdir() if f.is_file()}

bad = 0
for e in ledger:
    text = src.get(e["source"])
    if text is None:
        print(f"  原文が無い: {e['id']} → {e['source']}")
        bad += 1
    elif norm(e["quote"]) not in text:
        print(f"  引用が原文に無い: {e['id']}  {e['quote'][:60]}")
        bad += 1
print(f"引用: {len(ledger) - bad}/{len(ledger)} が原文に存在")

allowed = nums(" ".join([v for e in ledger for v in e.get("values", [])] + a.ignore))
for f in a.targets:
    found = nums(pathlib.Path(f).read_text(encoding="utf-8", errors="ignore"))
    outside = sorted(found - allowed)
    print(f"数字: {f}  {len(found)}件 / 台帳外 {len(outside)}件 {' '.join(outside)}")
    bad += len(outside)

print(f"判定: {'ALL OK' if bad == 0 else 'NG'}")
sys.exit(1 if bad else 0)
```

テスト用の台帳で回した出力です。`bad.txt` には「5割安く、料金は$0.25、出力は40%速い」と書いてあります。

```
引用: 2/2 が原文に存在
数字: good.txt  4件 / 台帳外 0件
数字: bad.txt  4件 / 台帳外 2件 $0.25 5割
判定: NG
```

「40%速い」が捕まっていないことに気づいたでしょうか。

### 照合器が何を見逃すかを、先に測る

照合が通っても、照合器が甘ければ意味がありません。Opus 5.5 の動画のときは、わざと誤った文を6つ作って通しました。

| 混ぜた誤り | 正しくは | 結果 |
|---|---|---|
| Opus 5.5 は 66.5% | 66.4% | 検出 |
| Opus 5 より5割安い | 4割 | 検出 |
| 18本中17本 合格 | 16本 | 検出 |
| $0.25 | $0.20 | 検出 |
| 6時間枠 | 5時間枠 | 検出 |
| 出力が40%速い | 30%以上 | **見逃し** |

最後の1つは、「40%」が台帳に（費用の値として）存在するので素通りします。数字の照合は「その値がどこかにあるか」しか見ていません。正しい値を別の文脈で使われると、捕まえられない。照合器を直せば済む話ではありませんでした。文を読む担当が、別に要ります。それが §2 の依頼文4です。

### 4-2. ファイルの抜けと孤児を数える ― `inventory.py`

161本の無音を見つけたのは、このスクリプトでした。参照と実ファイルを、両方向で突き合わせます。

```python
#!/usr/bin/env python3
"""参照と実ファイルを両方向で数える。欠落・孤児・破損疑いを出す。

使い方:
  # ソースの中に書かれたファイル名を拾う場合
  python inventory.py --src index.html js/*.js --assets assets/
  # ファイル名を計算で作っている場合（ハッシュ名など）は、期待リストを渡す
  python inventory.py --expected expected.txt --assets assets/voice/
"""
import argparse, pathlib, re, sys

p = argparse.ArgumentParser()
p.add_argument("--src", nargs="*", default=[], help="参照を探すファイル")
p.add_argument("--expected", help="期待するファイル名を1行1件で書いたテキスト")
p.add_argument("--assets", required=True, help="実ファイルのあるフォルダ")
p.add_argument("--ext", default="mp3,wav,ogg,png,jpg,jpeg,webp,svg,glb,json")
p.add_argument("--min-bytes", type=int, default=800, help="これ未満は破損疑い")
a = p.parse_args()

exts = [e.strip().lower() for e in a.ext.split(",")]
pat = re.compile(r"[\w\-./]+\.(?:%s)\b" % "|".join(map(re.escape, exts)), re.I)

refs = set()
for f in a.src:
    text = pathlib.Path(f).read_text(encoding="utf-8", errors="ignore")
    refs |= {pathlib.PurePosixPath(m).name for m in pat.findall(text)}
if a.expected:
    lines = pathlib.Path(a.expected).read_text(encoding="utf-8").splitlines()
    refs |= {pathlib.PurePosixPath(l.strip()).name for l in lines if l.strip()}

files = {f.name: f for f in pathlib.Path(a.assets).rglob("*")
         if f.is_file() and f.suffix[1:].lower() in exts}

missing = sorted(refs - files.keys())
orphan = sorted(files.keys() - refs)
tiny = sorted(n for n in refs & files.keys() if files[n].stat().st_size < a.min_bytes)

print(f"参照={len(refs)}  実ファイル={len(files)}  欠落={len(missing)}  "
      f"孤児={len(orphan)}  破損疑い(<{a.min_bytes}B)={len(tiny)}")
for label, items in (("欠落", missing), ("孤児", orphan), ("破損疑い", tiny)):
    for n in items[:50]:
        print(f"  {label}: {n}")
    if len(items) > 50:
        print(f"  {label}: ほか {len(items) - 50} 件")

sys.exit(1 if missing or tiny else 0)
```

```
参照=3  実ファイル=3  欠落=1  孤児=1  破損疑い(<800B)=1
  欠落: gone.png
  孤児: orphan.png
  破損疑い: b.png
```

- **欠落**があれば、そこは無音や画像切れになっています
- **孤児**があれば、何かを変えたのに気づいていません。こちらのほうが価値のある信号です

ファイル名を計算で作っている場合（台詞のハッシュを名前にしているなど）、ソースを文字で探しても参照は見つかりません。その場合は、同じ計算で「期待するファイル名の一覧」を書き出させて、`--expected` に渡します。161本はまさにこの形でした。

### 4-3. 公開物と手元を照合する ― `live_check.py`

多言語版で、翻訳ファイルのデプロイを忘れたことがあります。「翻訳が無ければ原文を出す」という安全な仕組みが働いて、全言語が完璧な日本語で表示されました。エラーはゼロ。手元のテストは全部通りました。手元には正しいファイルがあったからです。

以来、確認は公開されたものに対して行います。

```python
#!/usr/bin/env python3
"""手元のファイルと、公開されている実物が同じかをハッシュで比べる。

使い方:
  python live_check.py --base https://example.com/ index.html assets/voice/k123.mp3
"""
import argparse, hashlib, pathlib, sys, time, urllib.request

p = argparse.ArgumentParser()
p.add_argument("--base", required=True, help="公開URLの起点（末尾は / ）")
p.add_argument("files", nargs="+", help="手元のパス（公開URLでも同じ相対パスのもの）")
a = p.parse_args()

bad = 0
for f in a.files:
    local = hashlib.md5(pathlib.Path(f).read_bytes()).hexdigest()
    url = a.base.rstrip("/") + "/" + f.lstrip("./") + f"?nocache={int(time.time())}"
    try:
        with urllib.request.urlopen(url, timeout=20) as r:
            remote = hashlib.md5(r.read()).hexdigest()
    except Exception as e:
        remote = None  # 取れなかったものを「一致」や空で埋めない
        reason = type(e).__name__
    if remote is None:
        status = f"取得できなかった ({reason})"
    elif remote == local:
        status = "一致"
    else:
        status = "不一致（公開物が古い／別物）"
    bad += status != "一致"
    print(f"{status:<24} {f}")

print(f"判定: {'ALL OK' if bad == 0 else f'{bad} 件を確認して'}")
sys.exit(1 if bad else 0)
```

```
一致                       index.html
不一致（公開物が古い／別物）           assets/lang/en.json
取得できなかった (HTTPError)     assets/lang/ko.json
判定: 2 件を確認して
```

取得できなかったものを「一致」や空で埋めないのが大事です。数字はそろって見えるのに、判断の材料が静かに壊れます。

- **数字の入った文章を書かせたとき**：`check_ledger.py`

## 5. エージェントに毎回読ませる作業規約

ここまでの手順を、エージェントが毎回読む形にしたものです。リポジトリの直下に `CLAUDE.md`（Claude Code）や `AGENTS.md`（Codex など）として置きます。コードを書かない作業なら、チャットの最初に貼ってください。

```markdown
# 作業規約

## 1. 作る前に決めさせる
- 着手前に、私が決めるべきことを重要な順に最大5つ挙げる。選択肢と、選択による結果の違いも書く。
- 質問は一度に1つだけ。
- 案は2〜3個。各案に「狙い」「捨てたもの」「失敗する場面」を書く。
- 私が「これでいい」と言うまで着手しない。設計が2文でも、この確認は省かない。

## 2. 完了は観測で言う
- 着手前に、完了を確かめるコマンドと期待する出力を書く。
- 「完了しました」は、そのコマンドの実際の出力を添えたときだけ使う。添えられないときは「未検証」と書く。

## 3. 範囲を守る
- 変更した行は、すべて依頼にたどれること。頼まれていない改善は実装せず、最後に「提案」として書く。

## 4. 妥協を隠さない
- 品質を落とした版を、完成品として出さない。方針を変えたら、報告の最初の行でそう言う。
- 取得や計測に失敗した値を、0や空で埋めない。null にして「取得できなかった」と書く。

## 5. 数字は台帳から
- 数字の入った文章は、先に sources/ と ledger.json を作る。台帳に無い数字は書かない。

## 6. 公開物で確かめる
- 確認は手元ではなく、公開されたものに対して行う。反映を待つときは、新しい版にしか無い文字列で判定する。
- 公開・投稿・削除は、私の明示的な指示があるまで行わない。

## 7. 報告の形
- やったこと ／ 観測結果（コマンドと出力）／ やっていないこと ／ 私が判断すべきこと、の4つに分ける。
- 専門外の分野では、使った素材・設定・用語の名前を必ず書く。
```

- 7 の最後の行 → 専門外の語彙は、エージェントが毎回、素材と設定の名前を書いてきたことで覚えた

## 6. 運用でやりがちな失敗6つ

仕組みを入れたあとで踏みやすいものです。

**1. 審査を1体にまとめる**
全部を1体に見させると、平均的な指摘しか返ってきません。観点ごとに分けます。

**2. 点数の高い案を、そのまま出す**
審査の点数は、1行目の良し悪しを測れません。Opus 5.5 の動画の投稿文は、点数がいちばん高かった案の切り口で出して、読まれませんでした。1行目だけは、人が選びます。

**3. 直したあと、審査を回さない**
⑤は、1回目の指摘を直したときに入った誤りでした。直したら、もう一度回します。

**4. 照合が通ったら、安心する**
動画の6件は、全部、照合を通ったあとに見つかっています。照合器が何を見逃すかは、わざと誤りを混ぜて先に測っておきます。

**5. 案を5つ以上出させる**
選べなくなって、「おまかせで」に倒れます。3つまでにします。

**6. 手元で確かめて、公開したことにする**
手元の作業コピーは、いちばん信用できない場所です。確認は公開されたものに対して行います。
