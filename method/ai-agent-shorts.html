AIエージェントで1から作る — 1分AIニュース(YouTube Shorts)

エージェントに任せるには、
目視をやめるしかなかった

AIエージェントは、自分が作った動画を見られません。 mp4を渡しても再生できず、1本1,700枚のフレームを全部は確認できない。 だから「なんとなく良い」で回っていた判断を、全部数値と座標に置き換えました。 実際に事故を5件止めた、動画1本ぶんの設計を全部書き出します。

2026-09-12 ／ 1分AIニュース #01・#02 の制作から ／ 読了 約12分

01 — 制約

「良い感じにして」が、いちばん通じない指示だった

ずんだもんが最新のAIニュース5本を1分弱で読み上げるYouTube Shortsを、 AIエージェント(Claude Code)と一緒に作りました。台本作成から音声合成、 画面のレンダリング、投稿までを1本のパイプラインにしています。

最初に壁になったのは、技術的な難しさではありませんでした。 エージェントが、自分の作ったものを確認できないことです。

  • 出来上がったmp4を渡しても、エージェントは再生できない
  • フレームを画像で見せることはできるが、1本で1,700枚以上ある
  • 音は、そもそも聞けない

つまりエージェントは、自分の成果物に対して 「間延びしている」「字幕が読みにくい」「音が小さい」といった判断ができません。 人間が毎回見て、毎回指摘するしかない。それでは自動化した意味がありません。

しかも人間の目視は、思っていたより当てになりませんでした。
私が「重なっていない」と確認して投稿しようとしたものが、実機では全編にわたって重なっていた。

字幕とキャラクターが重なって見える、という指摘を受けて修正し、 フレームを何枚も並べて「解消した」と判断しました。ところが解消していませんでした。 重なっていたのは動画の内部ではなく、YouTube Shorts再生画面のUI (右側のいいね・コメント列、下部のタイトル欄)との間だったからです。 静止画をいくら眺めても、そこには写っていません。

02 — 原理

人間の目を、機械の数値に置き換える

そこで方針を変えました。エージェントに「見せる」ことを諦めて、 見なくても判定できる形に問題を書き直す。

人間が目で見ていたこと機械が測れる形不合格の線
間延びして見える静止フレーム比率(隣接フレームの画素差分が閾値未満の割合)1/3以上
画面が止まっている最長の静止区間3秒以上
字幕が読みにくい要素同士の矩形の交差判定1pxでも交差
暗すぎる冒頭0.5秒の平均輝度20/255未満
音が小さい / 割れているLUFS / dBTP-14±1.5を外れる / -1.0超
長すぎる尺60秒超

数値になった瞬間、エージェントは自分で回して、自分で直せるようになります。 「静止フレーム比率91%」と出れば、原因を探して修正し、もう一度測って14%になったことを確認できる。 人間の確認を待つ必要がありません。

閾値は、感覚を翻訳したもの

ここで大事なのは、閾値そのものに絶対的な根拠はない、ということです。 「静止フレーム比率1/3未満」は、私が過去に作った動画を見比べて 「これ以上止まっていると飽きる」と感じた線を、そのまま数字にしただけです。

根拠がなくても構いません。重要なのは 線が引かれていて、機械が同じ基準で何度でも測れることです。 線が間違っていたら、あとで動かせばいい。線が無いと、議論が毎回ゼロから始まります。

03 — 構造

5層に切って、エージェントが1層だけ触れるようにする

パイプライン全体を、依存の向きが一方向になるように5層へ分けました。 上の層を直しても下の層は影響を受けません。

層役割実体出力
1. データ内容を構造化データで持つbuild_news_shorts.pyscript.json
2. 合成音声を作る・口パクを作るsynth_long.py / lipsync_long.pywav / timing.json
3. 表現画面を描くscene_news.html(時刻→描画)
4. 検証合否を数値で出すqc_video.py ほか合格 / 不合格
5. 配信投稿・再生リスト・SNSupload_to_youtube.py ほかURL

データ層 — 内容は全部dictに置く

台本をHTMLに直接書くと、内容を1文字変えるのに表現も一緒に触ることになります。 そこで、1本のニュースが持つ情報を全部Pythonのdictで宣言する形にしました。 

dict(
  tag="sec", tagLabel="SECURITY", pose="review",
  audience="社内にサーバーがある人へ",          # 誰に関係あるか
  summary="AIエージェントが395組織を突破",      # 3秒で読める結論
  figs=[{"n":"395組織","l":"侵害された組織(48カ国)"},
        {"n":"7分","l":"侵入から管理者権限まで"}],
  diagram={"type":"score", ...},                # 図の種類とデータ
  impact="PaperCutは今すぐパッチ適用を",        # 読者がすべきこと
  text="ペーパーカットの脆弱性を突く攻撃で…",   # 読み上げ用(カタカナ込み)
  caption="PaperCutの脆弱性を突くAI主導の攻撃で…", # 字幕用(表記正しく)
  source="GreyNoise / BleepingComputer",
  source_url="https://www.bleepingcomputer.com/…",
  sourceType="調査",                            # 公式発表 / メディア報道 / 調査
)

読み上げ用の text と字幕用の caption を分けているのがポイントです。 音声合成には「ペーパーカット」とカタカナで渡さないと読みを間違えますが、 画面には「PaperCut」と正しく出したい。1つのフィールドで両立させようとすると必ず破綻します。

合成層 — ハッシュでキャッシュして、差分だけ作り直す

音声合成は1本あたり数十秒かかります。台本を1行直すたびに7本全部を作り直していては、 試行の回数が稼げません。そこで本文のハッシュをファイル名に入れました。 

th = hashlib.sha1((ln["text"] + str(sid)).encode()).hexdigest()[:10]
f = AUD / f"l_{ln['idx']:03d}_{sp}_{th}.wav"
if f.exists():
    sec = dur(f)          # 本文が同じなら再利用
else:
    vv(ln["text"], sid, f)  # 変わった行だけ合成

実際、事実確認で1行だけ修正が入ったとき、再合成されたのは 7本中1本だけでした。「新規合成 1 本」とログに出ます。

表現層 — 時刻を引数で受ける

ここが、この構成でいちばん効いた判断です。画面はHTML/CSSで作りますが、 CSSアニメーションや requestAnimationFrame は使いません。 代わりに、外から時刻を渡すと、その瞬間の画面を描く関数を1つ用意します。 

window.__setTime = function(t){
  $("pbar").style.width = (Math.min(t/TOTAL,1)*100) + "%";
  $("bgfx").style.transform =
    "translate("+(Math.sin(t*0.42)*230)+"px,"+(Math.cos(t*0.31)*300)+"px)";
  // …この時刻に表示すべきものを全部決める
};

レンダリング側は、時刻を進めながら1枚ずつ撮るだけです。

for i in range(N):
    pg.evaluate(f"window.__setTime({i/FPS:.4f})")
    pg.screenshot(path=str(FR/f"f_{i:05d}.jpg"), type="jpeg", quality=88)

この形にすると、レンダリングが実時間から切り離されます。 マシンが遅くてもコマ落ちしない。何度実行しても1フレームも違わない。 そして何より、検証スクリプトが任意の時刻の画面を再現できるようになります。 「t=26.0秒の状態を調べたい」が、そのまま __setTime(26.0) で書けます。

検証層 — 目視の代わりに座標を突き合わせる

要素同士が重なっていないかは、ブラウザに座標を聞けば分かります。 人間が画面を見て判断する必要はありません。 

def rects_overlap(a, b):
    ox = min(a["right"], b["right"]) - max(a["left"], b["left"])
    oy = min(a["bottom"], b["bottom"]) - max(a["top"], b["top"])
    if ox > 0 and oy > 0:
        return {"w": round(ox, 1), "h": round(oy, 1)}
    return None

これを0.1秒刻みで全編に回します。1本ぶんで500〜600回の判定になりますが、 数十秒で終わります。出力は1行です。 

ep02: 重なりなし(0.1秒刻み, 全587フレーム走査)

重要なのは、この検証が動画そのものではなくHTMLに対して走ることです。 mp4を作る前に判定できるので、レンダリングの2分を待つ必要がありません。

1本あたりの実測

2本目以降、1本を出すまでにかかっている時間です。

工程時間備考
ニュース収集・選定15〜20分一次ソースの確認を含む。ここだけ人間の判断が要る
台本作成10分データを書き換えるだけ。HTMLは触らない
音声合成〜ミックス3分変更した行だけ再合成
レンダリング2分1,700枚を撮ってmp4化
検証3種4分品質ゲート・要素の重なり・実機セーフゾーン
事実確認3分別エージェントに並列で投げる
投稿・再生リスト・SNS5分

金銭的なコストは、音声合成(VOICEVOX)が無料、レンダリングもローカルなので実質ゼロです。 X投稿のAPI利用料が1回$0.200かかる程度でした。

04 — 実際

この仕組みが実際に止めた、5つの事故

すべて、私の目視では見つけられなかった(あるいは見落とした)ものです。

① キャラクターが消えていた(画像404)

ローカルHTTPサーバのルート設定の都合で、キャラクター画像のパスが親ディレクトリを 参照しており、404になっていました。ところがレンダリングは成功扱いで終わります。 Playwrightの requestfailed はネットワークエラーでしか発火せず、 404はHTTPとして正常に返ってきているからです。 

# これだけでは404を取りこぼす
pg.on("requestfailed", lambda r: fails.append(r.url))
# ステータスコードも見る
pg.on("response", lambda r: fails.append(r.url) if r.status >= 400 else None)

「読込失敗0」というログを信じていたら、キャラのいない動画を投稿していました。

② 静止フレーム比率91%(背景が隠れていた)

背景に動く光を仕込んであったのに、その手前に不透明なパネルを置いていたため、 画面のほとんどが止まっていました。目で見ると「動いている」ように錯覚します。 文字が切り替わるからです。測ると91%が静止でした。

パネルの内側にも動く要素を足して14%まで下がりました。 測定はffmpegとnumpyだけでできます。 

diffs = [float(np.abs(arrs[i]-arrs[i-1]).mean()/255*100)
         for i in range(1, len(arrs))]
still_ratio = sum(1 for d in diffs if d < 0.5) / len(diffs)

③ 実機UIとの全編重なり(動画の中では重なっていない)

これが、目視がいちばん通用しなかった例です。動画の内部では、字幕もキャラクターも 一度も重なっていませんでした。座標判定でも「重なりなし」と出ます。 それでも実機では重なっていました。

YouTube Shortsの再生画面には、右側にいいね・コメント・シェアのボタン列が、 下部にタイトルとチャンネル名が動画の上に重ねて表示されます。 キャラクターは画面の右下にいたので、その両方に完全に埋もれていました。

解決は単純で、実機UIの占有領域も矩形として定義して、同じ交差判定にかけることです。 

# YouTube Shorts 実機UIの目安(1080x1920基準)
SAFE_RIGHT_W, SAFE_RIGHT_Y0, SAFE_RIGHT_Y1 = 220, 760, 1780  # 右のボタン列
SAFE_BOTTOM_H = 310                                          # 下のキャプション欄

測った結果は「キャラクターが2.2秒〜53.3秒のあいだ、右ボタン列と下キャプション欄の 両方と重なっている」。つまりほぼ全編でした。 字幕とキャラクターを安全領域に収め直して解消しています。

④ エンディングが0.02秒切れていた

最後の「チャンネル登録してくれたら…」が、わずかに切れて終わっていました。 原因は、動画全体の尺を最後の音声の終わりちょうどに合わせていたことです。

フレーム数は整数に丸められるので、48.117秒は1,443フレーム=48.10秒になります。 音声の終端48.12秒に対して0.02秒足りない。ffmpegの -shortest が 律儀に短い方に合わせていました。末尾に余韻を足すだけの修正です。 

TAIL = 0.7   # 最後の声にぴったり合わせると末尾が切れる
total += TAIL

⑤ 数字の誤帰属(事実確認エージェント)

「中国7ラボがClaudeを蒸留、1.5億回」と書いていました。出典を突き合わせたところ、 1.51億回はAlibaba系1社の数値で、7ラボ合計は約2億回。 間違いではないのに、合算と誤読される書き方でした。

これは数値測定では捕まりません。別のエージェントに 「台本の各数字を出典URLと突き合わせ、一致/要修正/確認不能で判定せよ」と投げています。 書いた本人とは別の文脈で読ませることに意味があります。

05 — 再現

あなたの題材でやるときの順番

動画である必要はありません。スライドでも、記事でも、アプリの画面でも同じです。

1. 先に「不合格の条件」を数値で書く

作り始める前に書きます。「良いもの」の定義は難しくても、 「これは出せない」の線なら引けます。最初は3つで十分です。 私の場合は、尺・音圧・静止比率から始めました。

2. データと表現を分ける

内容をJSONやdictに追い出します。判断基準は 「明日、内容だけ差し替えて2本目が作れるか」。 作れないなら、まだ表現に内容が埋まっています。

3. 表現層から時間を追い出す

アニメーションを実時間で動かすと、検証のたびに結果が変わります。 setTime(t) のように時刻を引数で受ける形にすると、 再現性と検証容易性が同時に手に入ります。これは動画以外でも効きます (状態を引数で受けるUIコンポーネント、と言い換えれば同じ話です)。

4. 検証をコマンド1つにする

python qc_video.py ep02 で全項目が測れて、 最後に「全項目通過」か「★不合格」の1行が出るようにします。 エージェントに渡すのはこのコマンドだけです。判断を挟ませません。

5. 事実は、書いた本人以外に検証させる

数値で測れるのは形式だけです。内容の正しさは別のエージェントに、 出典URLを渡して突き合わせさせます。「誇張されていないか」ではなく 「出典のどこに書いてあるか」を答えさせるのがコツです。

この5つを通すと、人間の仕事は「何を作るか」と「線をどこに引くか」だけになります。
「ちゃんとできているか」は、機械が毎回、同じ厳しさで見てくれます。

動くパイプライン一式について

この記事に書いた設計と、主要なコードはすべて公開しています。 ここまでの内容で、同じ構造を自分の題材で組み直すことはできます。

一方で、実際に動かすところまでには、記事に書ききれない細かい部分が残ります。 VOICEVOXの読み間違いの潰し方、口パクの閾値、BGMのダッキング設定、 YouTube APIの認証まわり、サムネの輝度調整といった、 「動くまでにハマる場所」です。

そこを含めた実行可能な一式を、別途配布する予定です。

含まれるもの中身
パイプライン本体台本生成・音声合成・口パク・ミックス・レンダリング(13スクリプト)
